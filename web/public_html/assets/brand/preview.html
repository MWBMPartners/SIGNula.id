SIGNula.id — Brand Assets first design pass

A horizontal key sliding into a lock, followed by a drawn-in checkmark — security, verification, and identity in one animated mark — paired with the "SIGNula.id" wordmark. Every file below lives in web/public_html/assets/brand/ and is a real, loadable asset (this page references the actual files, nothing here is a mock-up).

Palette

The codebase currently has two competing brand colours in play: the pre-launch teaser at web/public_html_landing/index.php uses teal (--primary:#1abc9c), while web/public_html/assets/css/main.css — used across login, dashboard, account, security, admin, and partner pages — already uses a blue→purple gradient. This pass adopts the existing blue→purple gradient as the one true brand palette, for three reasons: it already covers far more of the real, authenticated app than the single teaser page; blue-to-purple hues stay distinguishable under every common form of colour vision deficiency (unlike red/green or red/orange pairings); and it reads as more distinctive in the identity/SSO space than the ubiquitous "security teal/green" look. Nothing in this system uses red or green to convey meaning.

Live demo — theme override & motion

This is symbol-adaptive.svg embedded live via <object> (a real, running instance of the file, not a screenshot). The two buttons below exercise the two theme-control paths described in the file's own comments.

"Toggle light / dark" sets svg[data-theme] on the embedded document's root — the same hook an app would use if it inlines the SVG and controls it from JS (mirroring the existing html[data-theme] pattern already used on the landing page). "Simulate prefers-reduced-motion" is a preview-only stand-in for the OS setting (a real browser can't be told "pretend the user asked for reduced motion" from a button click), implemented by toggling an extra class the production files don't ship — the actual accessibility behaviour comes from the @media (prefers-reduced-motion: reduce) block inside each file, which responds to the visitor's real OS/browser setting with no JavaScript at all.

How the animation works: pure CSS @keyframes (no SMIL) — the key group (#key) slides in from off-canvas via translateX, then the checkmark badge fades in and its stroke draws on using stroke-dasharray/stroke-dashoffset, on a loop. Using CSS (rather than SMIL) means prefers-reduced-motion can turn it off declaratively, with no script required — it works even when the SVG is loaded as a plain <img>. Every animated file's fallback (non-animated) state is the fully-assembled "verified" look, so a renderer that doesn't execute CSS animations at all (some static rasterisers, print/export paths, ancient browsers) still shows the complete mark instead of a permanently missing checkmark.

Favicon & PWA icons

The full symbol's fine key-teeth detail doesn't survive down to 16–32px, so the favicon uses a simplified derivative: a bold gradient badge with a large keyhole cut-out plus the same checkmark badge. favicon.svg follows the OS theme automatically; favicon-light.svg / favicon-dark.svg are fixed-colour fallbacks. These are wired into web/public_html/assets/images/ (previously empty/missing — every app page's <link rel="icon"> was 404ing) and a real multi-resolution favicon.ico (16/32/48) plus the full PWA icon set declared in manifest.json (icon-72x72.png … icon-512x512.png) were rasterised from these sources and now exist on disk.

How to recolour (named layers)

Every file groups its shapes under semantic, stable IDs, so a part can be isolated, hidden, or restyled without touching geometry:

<g id="signula-lockup">
  <g id="symbol">
    <g id="key">   ... </g>
    <g id="lock">  ... </g>
    <g id="check"> ... </g>
  </g>
  <g id="wordmark"> ... </g>
</g>

Colour lives in CSS custom properties inside each file's own <style> (never hard-coded into an attribute), applied only through class selectors so var() substitution is always honoured:

/* inside e.g. lockup-light.svg */
svg { --sig-ink: #5568d3; --sig-accent: #764ba2; --sig-surface: #ffffff; --sig-text: #3d3d55; }
.sig-fill-ink { fill: var(--sig-ink); }
.sig-tick     { stroke: var(--sig-accent); }

To reskin: edit the four --sig-* values at the top of the file — no other markup changes needed. The mono files go further and use currentColor everywhere, so the entire mark recolours from a single color value:

<!-- shifts the whole mono mark to the brand's dark ink -->
<img src="lockup-mono.svg" style="color:#3d3d55">
<!-- or, if inlined -->
<svg id="signula-mark" style="color:#3d3d55">...</svg>

SVG-with-Base64-fallback pattern

Per the project brief's rule for icons/graphics ("SVG preferred, Base64-encoded fallback for clients that don't support it, detected dynamically where possible") — the same pattern AvatarService.php already uses for avatar fallbacks. <picture> is the standards-based way to do this: the browser uses the first <source> it supports, falling all the way back to the plain <img>'s src (which can be a Base64 data URI) if nothing else matches. 

<picture>
  <source srcset="/assets/brand/lockup-light.svg" type="image/svg+xml">
  <img
    src="data:image/png;base64,iVBORw0KGgoAAAANSUhEUgAA...(truncated, see lockup-fallback.png)"
    alt="SIGNula.id"
    width="420" height="100"
    loading="lazy"
  >
</picture>

Owner follow-ups

  • Approve the palette. This pass picked the existing blue→purple gradient over the teaser page's teal — reversible if you'd rather standardise on teal instead (all colour values are isolated in each file's <style> block, so a swap is mechanical).
  • Wordmark is text, not outlines. It uses the app's existing system font stack (renders correctly everywhere, stays editable/searchable), but that means its exact shape depends on whatever font the visitor's OS substitutes. A vector-perfect wordmark that renders pixel-identically everywhere would need converting this text to outlined paths — worth a follow-up pass once the wordmark treatment itself is approved.
  • PNG/ICO export — already done, not just noted. rsvg-convert + ImageMagick were available in this environment, so favicon.ico and the full 8-size manifest.json PWA icon set were actually rasterised, not left as a TODO.
  • Maskable safe-zone is a good-faith first pass, not pixel-audited against every Android launcher shape — icon-maskable.svg keeps content inside the standard 80% safe circle, but a dedicated maskable-icon QA pass (e.g. Chrome DevTools' maskable icon tester) is worth doing before shipping to production.
  • Verification caveat: this preview's screenshots during development were spot-checked with rsvg-convert (librsvg), which does not resolve CSS var() inside <style> blocks — so command-line rasterised previews can show shapes in black/white even though the same markup renders in full colour in every evergreen browser (Chrome, Firefox, Safari all fully support CSS custom properties inside SVG stylesheets). Please sanity-check the live colours by opening this page itself in a browser, not by re-rasterising the source files with an older SVG CLI tool.
