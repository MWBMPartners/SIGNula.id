GitHub OAuth Setup

GitHub OAuth enables developer-friendly authentication for your SIGNula instance. Popular for technical and developer-oriented user bases, SIGNula gets access to the user's profile, email addresses, and optionally organisation memberships.

Overview

GitHub OAuth provides a straightforward authentication flow for users with GitHub accounts. It is especially popular among developer communities and technical platforms. When a user authenticates via GitHub, SIGNula receives their username, display name, avatar URL, and email address(es). GitHub's OAuth implementation is simple to configure and does not require an app review process.

Quick Setup

Unlike some other OAuth providers, GitHub does not require an app review or approval process. Your OAuth App is immediately available for all GitHub users once created. This makes GitHub one of the fastest providers to set up.

Prerequisites

  • A GitHub account (free account is sufficient)
  • A publicly accessible domain with HTTPS enabled for your SIGNula instance
  • Access to the SIGNula Admin Panel
Simple requirements: GitHub OAuth has the simplest prerequisites of any login provider. No company page, developer program registration, or app review is needed.

Step-by-Step Setup

1

Go to GitHub Settings

Visit github.com, click your avatar in the top-right corner, and select Settings from the dropdown menu.

2

Open Developer Settings

Scroll to the very bottom of the left sidebar and click Developer settings. This section contains OAuth Apps, GitHub Apps, and personal access tokens.

3

Create a New OAuth App

Click OAuth Apps in the left sidebar, then click New OAuth App (or "Register a new application").

4

Fill in Application Details

Complete the registration form with the following details:

  • Application name: SIGNula Login
  • Homepage URL:
https://yourdomain.com
  • Application description: Universal single sign-on authentication
  • Authorization callback URL:
https://yourdomain.com/oauth/callback
Exact match required: GitHub requires the Authorization callback URL to match exactly, including the protocol, domain, path, and whether or not there is a trailing slash. Mismatches will result in an error during the OAuth flow.
5

Register the Application

Click Register application. You will be taken to the app's settings page.

6

Copy the Client ID

The Client ID is displayed on the app page. Copy this value. 

Iv1.xxxxxxxxxxxxxxxx
7

Generate a New Client Secret

Click the Generate a new client secret button. A new secret will be generated and displayed.

Critical: Copy the Client Secret immediately. GitHub will not show the full secret again after you navigate away from this page. If you lose it, you will need to generate a new one (which invalidates the old one).
8

Copy the Client Secret

Copy the generated Client Secret string and store it in a secure location such as a password manager. The secret will look something like: 

xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
9

Configure SIGNula Admin Panel

Log in to your SIGNula Admin Panel and navigate to:

System → OAuth Providers → GitHub

  1. Toggle the Enabled switch to activate GitHub OAuth.
  2. Paste your Client ID into the "Client ID" field.
  3. Paste your Client Secret into the "Client Secret" field.
  4. Click Save.
Security: The Client Secret is stored encrypted in tblSettings (marked as isSensitive) and is never exposed in the admin UI after saving.
10

Test the Login

Open your SIGNula login page and click the Sign in with GitHub button. You should be redirected to GitHub's authorisation page, and upon approval, returned to SIGNula with your account linked.

Success: If login completes without errors and your GitHub profile information (username, avatar, email) appears in SIGNula, the integration is working correctly.

Scopes & Permissions

SIGNula requests the following OAuth scopes from GitHub:

Scope Description Required
(no scope) Default access: grants read-only access to public profile information (username, avatar URL, bio). Default
user:email Access to the user's email addresses, including their primary and verified emails. Essential for account linking. Yes
read:user Full read access to the user's profile data, including private profile information. Yes
read:org Read access to the user's organisation memberships. Useful if you need to restrict access based on organisation membership. Optional
Private emails: Many GitHub users have their email address set to private. Without the user:email scope, you will not receive any email address. SIGNula always requests this scope to ensure reliable account linking.

OAuth App vs GitHub App

GitHub offers two types of applications: OAuth Apps and GitHub Apps. Understanding the difference is important when setting up SIGNula.

Feature OAuth App GitHub App
Purpose User authentication and basic profile access Complex integrations with repos, issues, actions, etc.
Setup complexity Simple More complex (requires webhook URL, permissions matrix)
Best for SSO Yes - recommended for SIGNula Overkill for authentication-only use cases
Rate limits 5,000 requests/hour per authenticated user Higher limits, installation-based
Granular permissions Scope-based Fine-grained repository/org permissions
Recommendation: SIGNula uses an OAuth App, which is simpler and perfectly suited for single sign-on authentication. GitHub Apps are designed for more complex integrations (such as CI/CD tools, bots, or repository management) and are not needed for SSO.

Important Notes

Client Secret Visibility

The Client Secret is only displayed in full immediately after generation. Once you navigate away, GitHub masks the secret. If you lose it, you must generate a new one, which will invalidate the previous secret. Remember to update SIGNula's settings if you regenerate.

Email Handling

GitHub provides both primary and verified emails via the /user/emails endpoint. Some users may have multiple email addresses. SIGNula uses the primary verified email for account linking. If no verified email is found, the user will be prompted to provide one manually.

Rate Limits

Authenticated requests to the GitHub API are limited to 5,000 requests per hour per user token. For authentication-only usage, this limit is more than sufficient. Monitor the X-RateLimit-Remaining response header if needed.

Secret Rotation

GitHub allows you to have up to two active client secrets simultaneously. This enables zero-downtime secret rotation: generate a new secret, update SIGNula, verify it works, then delete the old secret.

Troubleshooting

  • GitHub requires an exact match for the Authorization callback URL, including the trailing slash (or lack thereof).
  • Verify the callback URL in your GitHub OAuth App settings matches exactly: https://yourdomain.com/oauth/callback
  • Ensure the protocol is https:// (not http://).
  • Check the oauth.github.redirect_uri setting in SIGNula matches the GitHub configuration.
  • Note: https://yourdomain.com/oauth/callback and https://yourdomain.com/oauth/callback/ are treated as different URLs.

  • Verify the Client ID in SIGNula matches the one shown on the GitHub OAuth App page.
  • The Client Secret may have been regenerated or expired. Check if the secret in SIGNula matches the active secret in GitHub.
  • If you recently regenerated the secret, update the oauth.github.client_secret setting in SIGNula.
  • Ensure there are no extra whitespace characters in the Client ID or Secret fields.

  • GitHub limits authenticated requests to 5,000 per hour per user token.
  • Check the X-RateLimit-Remaining header in API responses to monitor usage.
  • If you are hitting rate limits during normal authentication, there may be an issue with excessive API calls. Review the SIGNula activity log.
  • Rate limits reset every hour. The reset time is indicated in the X-RateLimit-Reset header (Unix timestamp).

  • The user may have their email set to private in their GitHub profile settings.
  • Ensure the user:email scope is included in SIGNula's OAuth request. Without this scope, private emails are not accessible.
  • SIGNula uses the /user/emails endpoint (which requires the user:email scope) to retrieve all email addresses, including private ones.
  • If no verified email is available, SIGNula will prompt the user to enter an email manually during account creation.

  • GitHub allows up to two active client secrets simultaneously for zero-downtime rotation.
  • To rotate: generate a new secret in GitHub, update SIGNula with the new secret, verify login works, then delete the old secret in GitHub.
  • Remember that SIGNula stores the secret encrypted. After updating, verify the new secret is working by testing the login flow.
  • Old tokens issued with the previous secret will continue to work until they expire.

Settings Reference

These settings are stored in tblSettings in the SIGNula backend database. Fields marked with are encrypted at rest.

Setting Key Type Description
oauth.github.enabled Boolean Enable or disable GitHub OAuth as a login provider
oauth.github.client_id String Your GitHub OAuth App Client ID
oauth.github.client_secret String Your GitHub OAuth App Client Secret (encrypted, isSensitive)
oauth.github.redirect_uri String OAuth callback URL (e.g., https://yourdomain.com/oauth/callback)
oauth.github.scopes String Space-separated list of OAuth scopes. Default: read:user user:email
