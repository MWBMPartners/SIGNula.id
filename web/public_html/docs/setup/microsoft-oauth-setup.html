Microsoft OAuth Setup

Configure Microsoft Identity Platform v2.0 to enable sign-in with personal Microsoft accounts and Microsoft 365 Work/School accounts via Azure Entra ID (formerly Azure AD).

Overview

Microsoft OAuth supports authentication with personal Microsoft accounts (e.g., @outlook.com, @hotmail.com, @live.com) as well as Microsoft 365 Work/School accounts (organisational accounts managed via Azure Entra ID). SIGNula uses the Microsoft Identity Platform v2.0 endpoints for authentication.

SIGNula requests the following scopes from Microsoft by default:

  • openid — Enables OpenID Connect single sign-on
  • profile — Access to user's display name and basic profile
  • email — Access to the user's email address
  • User.Read — Read the user's Microsoft Graph profile
  • offline_access — Enables refresh tokens for long-lived sessions
Note: Microsoft Identity Platform v2.0 supports both personal and organisational accounts through a single application registration, depending on the tenant configuration you choose.

Prerequisites

  • A Microsoft account (personal, or Work/School with admin access)
  • Access to the Azure Portal
  • A registered domain for your SIGNula installation
  • HTTPS enabled on your domain (required by Microsoft for redirect URIs)

Step-by-Step Setup

1

Go to Azure Portal

Navigate to portal.azure.com and sign in with your Microsoft account. You can use either a personal account or a Work/School account with administrative privileges.

2

Navigate to App Registrations

Go to Azure Active Directory (or Microsoft Entra ID) → App registrations. Alternatively, search for "App registrations" in the top search bar.

3

Register a New Application

Click New registration and fill in the following:

  • Name: SIGNula Authentication
  • Supported account types: Choose based on your requirements:
    Option Description
    Accounts in any organisational directory and personal Microsoft accounts Recommended — Multi-tenant + personal accounts. Allows both Work/School and personal Microsoft accounts.
    Accounts in any organisational directory only Multi-tenant Work/School accounts only. No personal accounts.
    Personal Microsoft accounts only Only personal accounts (@outlook.com, @hotmail.com, etc.).
  • Redirect URI:
    • Platform: Web
    • URI:
      https://yourdomain.com/oauth/callback

Click Register.

4

Copy the Application (Client) ID

After registration, you will be taken to the app's Overview page. Copy the Application (client) ID — this is your Client ID.

Application (client) ID: xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx
5

Note the Directory (Tenant) ID

On the same Overview page, note the Directory (tenant) ID. If you chose multi-tenant support, you will typically use common instead of a specific tenant ID (see the Tenant Configuration section below).

Directory (tenant) ID: xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx
6

Create a Client Secret

Navigate to Certificates & secrets in the left sidebar, then click New client secret.

  • Description: SIGNula Auth
  • Expiry: Choose a duration (recommended: 24 months)

Click Add.

Critical: Copy the secret VALUE immediately! It will only be displayed once. If you navigate away without copying it, you will need to create a new secret. Do not copy the "Secret ID" — you need the "Value" column.
Reminder: Client secrets expire. Set a calendar reminder to rotate the secret before it expires. When a secret expires, users will be unable to sign in with Microsoft until a new secret is configured.
7

Configure API Permissions

Navigate to API permissions in the left sidebar, then click Add a permission.

  • Select Microsoft Graph
  • Choose Delegated permissions
  • Add the following permissions:
    • openid
    • profile
    • email
    • User.Read
    • offline_access

If you have admin access to your Azure tenant, click "Grant admin consent for [your organisation]" to pre-approve these permissions for all users in your organisation.

Note: The openid, profile, email, and offline_access scopes are pre-approved by default for most tenants and do not require admin consent.
8

Configure SIGNula Admin Panel

Log in to your SIGNula Admin Panel and navigate to System → OAuth Providers → Microsoft.

  • Enter the Client ID (Application ID)
  • Enter the Client Secret (the Value you copied)
  • Tenant ID: Enter your specific tenant ID, or use common for multi-tenant support
  • Click Save
Security: Both the Client ID and Client Secret are stored encrypted at rest in the SIGNula database using cryptographic encryption with salt.
9

Test the Integration

Visit your SIGNula login page and click the "Sign in with Microsoft" button. You should be redirected to the Microsoft sign-in page. After authenticating and granting consent, you will be redirected back to SIGNula and logged in.

Tip: Test with both a personal Microsoft account and an organisational account (if applicable) to verify that both flows work correctly.

Tenant Configuration

The Tenant ID controls which types of accounts can authenticate with your SIGNula installation. Microsoft supports several tenant values:

Tenant Value Accounts Allowed When to Use
common All Microsoft accounts (personal + any organisation) Recommended for most SIGNula installations. Allows the broadest range of users to authenticate.
organizations Work/School accounts from any Azure AD tenant Use when you want to restrict access to organisational accounts only (no personal accounts).
consumers Personal Microsoft accounts only Use when you want to restrict access to personal accounts only (no Work/School).
Specific Tenant ID Users from a single specific Azure AD tenant Use when you want to restrict access to a single organisation. Users from other organisations cannot sign in.
Endpoint Format: The authorization and token endpoints use the tenant value in the URL: https://login.microsoftonline.com/{tenant}/oauth2/v2.0/authorize

Microsoft 365 Work/School

When users sign in with a Microsoft 365 Work/School account, additional organisational context is available through the Microsoft Graph API.

Organisational Account Setup

For organisations using Microsoft 365, a tenant administrator may need to grant consent for SIGNula to access user profile information. This can be done in two ways:

  • User consent: Each user grants permission when they first sign in (if tenant policy allows)
  • Admin consent: A tenant administrator pre-approves the application for all users via the Azure Portal or by navigating to the admin consent URL

Admin Consent Flow

To trigger the admin consent flow, redirect an administrator to:

https://login.microsoftonline.com/{tenant}/adminconsent? client_id=YOUR_CLIENT_ID& redirect_uri=https://yourdomain.com/oauth/callback& scope=openid profile email User.Read offline_access

Microsoft Graph API Access

With the User.Read scope, SIGNula can retrieve additional profile information from the Microsoft Graph API, including the user's display name, job title, department, office location, and profile photo.

Troubleshooting

AADSTS50011 — Reply URL Mismatch

The redirect URI in the OAuth request does not match any of the registered redirect URIs for the application. Go to the Azure Portal → App registrations → your app → Authentication, and verify the redirect URI matches exactly (including protocol, domain, and path).

AADSTS7000215 — Invalid Client Secret

The client secret provided is invalid or has expired. Navigate to Certificates & secrets in the Azure Portal and check that the secret has not expired. If it has, create a new secret and update it in the SIGNula Admin Panel.

AADSTS65001 — Consent Required

The user or administrator has not consented to the requested permissions. This typically occurs in organisations with strict consent policies. The tenant administrator needs to grant admin consent via the Azure Portal or the admin consent URL.

AADSTS700016 — Application Not Found

The application was not found in the specified tenant. Verify that the Client ID is correct and that the application registration has not been deleted. If using a specific tenant ID, ensure the application is registered in (or available to) that tenant.

Tenant Restriction Issues

If users from certain organisations cannot sign in, check the Supported account types in your app registration. Ensure you have selected the appropriate option for your use case. Also verify the tenant value in SIGNula matches your intended audience (e.g., common for broadest access).

Settings Reference

These settings are stored in tblSettings in the SIGNula backend database. Fields marked with are encrypted at rest.

Setting Key Type Description
oauth.microsoft.enabled Boolean Enable or disable Microsoft as a login provider
oauth.microsoft.client_id String Application (client) ID from Azure App Registration (encrypted, isSensitive)
oauth.microsoft.client_secret String Client secret value from Azure (encrypted, isSensitive)
oauth.microsoft.tenant_id String Tenant ID or alias. Options: common, organizations, consumers, or a specific tenant GUID. Default: common
oauth.microsoft.redirect_uri String Redirect URI after Microsoft authentication (auto-configured)
oauth.microsoft.scopes JSON JSON array of OAuth scopes. Default: ["openid","profile","email","User.Read","offline_access"]
oauth.microsoft.secret_expiry Date Expiry date of the client secret (for rotation reminders)
oauth.microsoft.prompt String OAuth prompt parameter. Options: login, consent, select_account, none. Default: select_account
