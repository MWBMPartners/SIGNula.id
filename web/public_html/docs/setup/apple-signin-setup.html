Apple Sign In Setup

Configure Sign In with Apple for privacy-focused authentication. Apple provides a unique, secure sign-in experience with built-in private email relay support.

Overview

Sign In with Apple provides a privacy-focused authentication mechanism for SIGNula users. Unlike other OAuth providers, Apple has several unique characteristics that require special handling:

  • User name is only shared on the first sign-in. Subsequent sign-ins will not include the user's name. SIGNula must store the name during the initial authorisation.
  • Private Email Relay: Users can choose to hide their real email address. Apple generates a unique, anonymous relay address (e.g., xxxxx@privaterelay.appleid.com) that forwards to the user's real email.
  • JWT Client Authentication: Apple uses ES256-signed JWTs for client authentication instead of a simple client_secret string.
  • Form POST Response Mode: Apple returns authentication data via form_post (HTTP POST) rather than query parameters.
Important: Because Apple only provides the user's name on the first authorisation, SIGNula must capture and store this information immediately. If the initial callback is not processed correctly, the name will be permanently unavailable via Apple's API.

Prerequisites

  • An Apple Developer account ($99/year) — developer.apple.com/programs
  • Access to developer.apple.com → Certificates, Identifiers & Profiles
  • A registered domain for your SIGNula installation
  • HTTPS enabled on your domain (required by Apple)
  • The ability to host a domain verification file on your web server
Note: An Apple Developer account requires an annual fee of $99 USD. This is required to access the Sign In with Apple service, create keys, and register Service IDs.

Step-by-Step Setup

1

Go to Apple Developer Portal

Navigate to developer.apple.com, sign in with your Apple ID, and go to Certificates, Identifiers & Profiles.

2

Register an App ID

If you do not already have an App ID registered, create one:

  1. Go to Identifiers → click the + button
  2. Select App IDs → click Continue
  3. Select type: App
  4. Description: SIGNula
  5. Bundle ID: com.yourdomain.signula (Explicit)
  6. Under Capabilities, enable "Sign In with Apple"
  7. Click Continue → Register
3

Register a Services ID

A Services ID is required for web-based Sign In with Apple (as opposed to native iOS/macOS apps).

  1. Go to Identifiers → click the + button
  2. Select Services IDs → click Continue
  3. Description: SIGNula Web Login
  4. Identifier: com.yourdomain.signula.web
  5. Click Continue → Register
Important: The Services ID identifier must be different from your App ID Bundle ID. The Services ID identifier is what you will use as the client_id in SIGNula.
4

Configure the Services ID

After registering the Services ID, configure it for Sign In with Apple:

  1. Click on the newly created Services ID in the Identifiers list
  2. Enable "Sign In with Apple" checkbox
  3. Click Configure
  4. Primary App ID: Select your App ID (created in Step 2)
  5. Website URLs:
    • Domains: yourdomain.com (without https://)
    • Return URLs:
      https://yourdomain.com/oauth/callback
  6. Click Save → Continue → Save
Domain Verification: Apple may require you to verify domain ownership by placing a verification file at https://yourdomain.com/.well-known/apple-developer-domain-association.txt. Download this file from the Apple Developer portal when prompted and upload it to your server.
5

Create a Sign In with Apple Key

Apple uses a private key (rather than a client secret) for authentication. You must generate a key specifically for Sign In with Apple.

  1. Go to Keys → click the + button (Create a new key)
  2. Key Name: SIGNula Sign In Key
  3. Enable "Sign In with Apple" → click Configure
  4. Primary App ID: Select your App ID
  5. Click Save → Continue → Register
  6. Download the .p8 key file immediately
  7. Note the Key ID displayed on the confirmation page
Critical: You can only download the .p8 key file ONCE. If you lose it, you will need to revoke the key and create a new one. Store this file in a secure location immediately after downloading.

The downloaded file will look like:

-----BEGIN PRIVATE KEY----- MIGTAgEAMBMGByqGSM49AgEGCCqGSM49AwEHBHkwdwIBAQQg... (multiple lines of base64 encoded key data) ... -----END PRIVATE KEY-----
6

Note Your Team ID

Your Team ID is a 10-character alphanumeric string that identifies your Apple Developer account. You can find it in:

  • The top-right corner of the Apple Developer portal
  • Account → Membership Details
Team ID: XXXXXXXXXX (10 characters)
7

Configure SIGNula Admin Panel

Log in to your SIGNula Admin Panel and navigate to System → OAuth Providers → Apple.

  • Client ID: Enter the Services ID identifier (e.g., com.yourdomain.signula.web)
  • Team ID: Your 10-character Team ID
  • Key ID: The Key ID from Step 5
  • Private Key: Paste the full contents of the .p8 file, including the -----BEGIN PRIVATE KEY----- and -----END PRIVATE KEY----- lines
  • Click Save
Security: The private key is stored encrypted at rest in the SIGNula database using cryptographic encryption with salt (marked as isSensitive).
8

Test the Integration

Visit your SIGNula login page and click the "Sign in with Apple" button. You will be redirected to Apple's sign-in page. After authenticating with your Apple ID, you will be asked to choose whether to share your real email or use a private relay address, and then redirected back to SIGNula.

Tip: On your first test, verify that SIGNula captures and stores the user's name correctly. Sign out and sign in again to confirm that subsequent logins work even without the name being provided by Apple.

How Apple Sign In Works (Technical)

Apple's authentication flow differs significantly from other OAuth providers. Here is how SIGNula handles the Sign In with Apple process:

JWT Client Secret Generation

Instead of using a static client secret, SIGNula generates a short-lived JWT (JSON Web Token) that serves as the client_secret. This JWT is signed using the ES256 (ECDSA with P-256 curve and SHA-256) algorithm.

// JWT Header { "alg": "ES256", "kid": "YOUR_KEY_ID" } // JWT Payload (Claims) { "iss": "YOUR_TEAM_ID", "iat": 1708300800, "exp": 1708387200, "aud": "https://appleid.apple.com", "sub": "com.yourdomain.signula.web" } // The JWT is signed with your .p8 private key

Authentication Flow

  1. SIGNula redirects the user to Apple's authorisation endpoint with the Services ID as client_id
  2. The user authenticates with their Apple ID (Face ID, Touch ID, or password)
  3. Apple returns an authorisation code via form_post (HTTP POST to the return URL)
  4. SIGNula generates a JWT client_secret using the ES256 algorithm and private key
  5. SIGNula exchanges the authorisation code for tokens using the generated client_secret
  6. The ID token is decoded to extract the user's information
Form POST Response Mode: Apple sends authentication data via an HTTP POST request (not a URL query parameter redirect). SIGNula's callback handler reads the data from the POST body ($_POST) rather than from $_GET.

First Sign-In vs Subsequent Sign-Ins

On the first sign-in, Apple includes a user JSON object in the POST body containing the user's name (first name and last name). This is the only time this data is provided. On all subsequent sign-ins, only the code and id_token are returned.

Private Email Relay

Apple's Private Email Relay allows users to hide their real email address when signing in. When a user chooses "Hide My Email", Apple generates a unique relay address in the format:

xxxxxxxxxxxxxxxxxxxxxxxx@privaterelay.appleid.com

How It Works

  • Emails sent to the relay address are forwarded to the user's real email address
  • The relay address is unique per app — different apps receive different relay addresses for the same user
  • The user can disable forwarding at any time from their Apple ID settings

Mail Server Configuration

To send emails to private relay addresses, your mail server must be registered with Apple:

  1. Go to developer.apple.com → Certificates, Identifiers & Profiles
  2. Navigate to Services → Sign in with Apple for Email Communication
  3. Register your outbound email domains and/or individual email addresses
  4. Verify domain ownership via SPF and DKIM records
Important: If your mail server is not registered with Apple, emails sent to @privaterelay.appleid.com addresses will bounce. This affects password reset emails, notifications, and any other communications from SIGNula.

Important Limitations

Name Only Available on First Authorisation

Apple only provides the user's name (first and last) during the very first authorisation. If the user revokes access and re-authorises, the name is provided again. However, this is the only mechanism to re-obtain the name. SIGNula must store the name immediately when first received.

Private Relay Emails Require Special Configuration

As described above, sending emails to @privaterelay.appleid.com addresses requires registering your sending domains/addresses with Apple. Without this configuration, transactional emails will not be delivered to users who chose "Hide My Email".

Keys Expire and Need Rotation

Sign In with Apple keys do not technically expire, but Apple recommends rotating keys periodically for security. You can have up to two active keys at a time, which allows for seamless rotation: create a new key, update SIGNula to use it, then revoke the old key.

.p8 File Can Only Be Downloaded Once

The private key file (.p8) is only available for download at the moment of creation. If lost, the key must be revoked and a new one created. Store the file securely (e.g., in a password manager or encrypted vault) immediately after downloading.

Troubleshooting

invalid_client — Wrong Client ID

This error typically occurs when you are using the App ID Bundle ID instead of the Services ID identifier as the client_id. For web-based Sign In with Apple, the client_id must be the Services ID (e.g., com.yourdomain.signula.web), not the App ID (e.g., com.yourdomain.signula).

JWT Generation Failures

If SIGNula fails to generate the JWT client_secret, check the following:

  • The private key is correctly pasted in the SIGNula admin panel (including BEGIN/END lines)
  • The Key ID matches the key associated with your .p8 file
  • The Team ID is correct (10-character alphanumeric string)
  • Your PHP installation has the OpenSSL extension enabled with ES256 support

Key File Issues

If the .p8 key file appears corrupted or invalid, ensure that no extra whitespace, line breaks, or encoding issues were introduced when pasting the key contents. The key should be in PEM format with exactly the -----BEGIN PRIVATE KEY----- and -----END PRIVATE KEY----- delimiters.

Domain Verification Problems

If Apple cannot verify your domain, ensure that:

  • The verification file is accessible at https://yourdomain.com/.well-known/apple-developer-domain-association.txt
  • The file is served with the correct content type
  • There are no redirects (e.g., HTTP to HTTPS, www to non-www) that might prevent Apple from accessing the file
  • The domain in the Services ID configuration matches exactly (no protocol prefix, no trailing slash)

Settings Reference

These settings are stored in tblSettings in the SIGNula backend database. Fields marked with are encrypted at rest.

Setting Key Type Description
oauth.apple.enabled Boolean Enable or disable Apple as a login provider
oauth.apple.client_id String Services ID identifier (e.g., com.yourdomain.signula.web). This is NOT the App ID.
oauth.apple.team_id String Your 10-character Apple Developer Team ID
oauth.apple.key_id String The Key ID associated with your Sign In with Apple key
oauth.apple.private_key Text Full contents of the .p8 private key file, including BEGIN/END delimiters (encrypted, isSensitive)
oauth.apple.redirect_uri String Return URL after Apple authentication (auto-configured)
oauth.apple.scopes JSON JSON array of requested scopes. Default: ["name","email"]
oauth.apple.response_mode String Response mode for Apple's callback. Fixed: form_post
