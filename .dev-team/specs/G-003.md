# G-003 — JWT API Authentication (Bearer tokens for the REST API)

> **Gate item:** #41 / B-006 / FG-004 · **Status:** spec (queued, gated — auth-critical + dependency decision)
> **Build order:** **FIRST.** G-001 (SIGNula-as-IdP) reuses this spec's signing keys, JWKS endpoint, and JWT
> sign/verify primitives — do not start G-001 until Stages 1–4 here are merged.
> **Author altitude:** this is the build contract. Implementers follow it; deviations get logged in the Decision log below.

## 1. What & why

Today the SIGNula REST API (`web/public_html/api/v1/index.php` → `Router` → `BaseController`) authenticates a
request in exactly three ways, in this precedence order (grounded in `BaseController::getCurrentUser()`,
lines 157–177):

1. **Browser session** — `$_SESSION['user_id']` → `getUserById()` (works).
2. **Bearer token** — `Router::getBearerToken()` → `getUserByToken()` — **a stub**:
   ```php
   private function getUserByToken(string $token): ?array
   {
       // TODO: Implement JWT validation
       // For now, return null
       return null;
   }
   ```
   (`web/private_html/api/BaseController.php` lines 208–213.)
3. **API key** — `X-API-Key` header or `?api_key=` → `getUserByApiKey()` (works; SHA-256 hash lookup against
   `tblAPIKeys`, see `APIKeyManager::validateKey()`).

So a client can present `Authorization: Bearer <jwt>` and the API silently treats it as *unauthenticated*
(falls through to the API-key branch, then returns `null`). The brief mandates a **"FULLY SECURE" JSON REST
API following current and future industry standards**; bearer-token auth is table-stakes (9/10 comparable
CIAM platforms per FEATURES.md FG-004) and is the substrate the IdP epic (G-001) issues tokens *through*.

**This spec implements proper JWT bearer authentication:** a token-issuance endpoint, refresh-token rotation
with reuse detection, a revocation/denylist, a public JWKS endpoint, and the wiring so `requireAuth()`
accepts a Bearer JWT alongside the existing `X-API-Key` and session paths — **without breaking either.**

### Why JWT *and* keep API keys

| Auth method | Who | Lifetime | Carries | Keep? |
|---|---|---|---|---|
| Browser session | end-users in a browser | session (DB-backed `tblSessions`) | `user_id` | yes — unchanged |
| **API key** (`sk_live_…`) | **partner servers** (machine, long-lived secret) | until revoked | `partnerID` | **yes — unchanged** |
| **JWT access token** (NEW) | end-users via SPA/mobile/embedded apps; short-lived M2M | minutes | `userID` (+ later partner/client) | NEW |

API keys are a *partner/server* credential keyed to `partnerID`; JWTs are a *user-session* credential keyed to
`userID` (the `sub` claim). They are complementary, not redundant — both must coexist.

## 2. Scope

### In scope
- A signed-JWT **access token** (short-lived) + **refresh token** (rotating, reuse-detected) model.
- RS256 asymmetric signing with a **public JWKS** endpoint so any verifier (including future G-001 RPs and
  third-party services) can validate tokens without a shared secret.
- Key storage (encrypted private key in `tblSettings` `isSensitive`, with a `_private` key-file fallback per
  brief), `kid`-based key selection, and a key-**rotation** procedure.
- Endpoints: `POST /api/v1/auth/token`, `POST /api/v1/auth/refresh`, `POST /api/v1/auth/revoke`,
  `GET /.well-known/jwks.json`.
- Implementing `BaseController::getUserByToken()` for real and wiring it into `requireAuth()`.
- A self-hosted JWT implementation (no Composer in prod).
- New tables for refresh tokens + a jti denylist; a settings block; one migration (`025`).
- Unit tests for sign/verify/expiry/tamper/alg-confusion/`none`/revocation/clock-skew.

### Out of scope (explicitly)
- **OAuth 2.0 / OIDC authorization-server semantics** (`/authorize`, `/token` grant types, consent,
  client registration, `id_token`, `/userinfo`, discovery) — that is **G-001**. G-003 only builds the
  *foundation*: the JWT sign/verify class, the signing keys, the JWKS endpoint, the revocation model. G-001's
  `id_token`/access-token issuance must reuse `JWT::sign()` / `KeyManager` / the JWKS endpoint built here —
  **design these as the public, reusable surface.**
- Replacing API-key auth (kept as-is).
- SCIM, SAML, push-MFA (other FGs).

## 3. JWT library decision — **vendor `firebase/php-jwt` source into `web/_lib/jwt/`**

### The constraint
Dreamhost shared hosting, no CLI, no Composer in prod. The project already proves the self-hosting pattern:
`web/_lib/` vendors `crawlerdetect/` and `tcpdf/` as plain source, loaded by the directory-scanning autoloader
+ explicit `require_once`. `composer.json` requires only `php >=8.3`; runtime classes are require-based, not
PSR-4-autoloaded in prod.

### Options compared

**Option A — Vendor `firebase/php-jwt` (v6.x) source into `web/_lib/jwt/`.** *(CHOSEN)*
- Pros: the de-facto PHP JWT library; audited, widely used, handles RS256/HS256/ES256, `kid` header,
  `JWK::parseKeySet()` for JWKS, leeway/clock-skew, and — critically — **explicit algorithm allowlisting**
  (`JWT::decode($jwt, $keyOrKeySet)` where the allowed alg is pinned by the `Key` object, which is the standard
  mitigation for the alg-confusion / `none` family of attacks). MIT-licensed. Source is ~6 files, zero runtime
  Composer deps (it has an optional `Firebase\JWT\JWK` that needs no extra packages; only ext-openssl which
  Dreamhost has).
- Cons: must manually track upstream security releases (mitigate: pin version in a `web/_lib/jwt/VERSION`
  file + note in `_docs/setup/SECURITY_SETUP.md`; subscribe to its GHSA feed). Namespaced (`Firebase\JWT\`)
  — fine, we `require_once` the files explicitly like any vendored lib; namespacing actually *helps* avoid
  collisions.
- **Fit:** matches the established `_lib/` precedent exactly, is battle-tested for the exact attack class we
  care about (alg confusion), and is small enough to vendor cleanly.

**Option B — Minimal in-house RS256/HS256 JWT class.**
- Pros: zero third-party code; the project *already has a working in-house JWS signer* —
  `AppleOAuth::generateClientSecret()` (`web/private_html/auth/providers/AppleOAuth.php` lines ~206–260)
  hand-rolls a JWS: `base64UrlEncode(header) . '.' . base64UrlEncode(payload)` signed with `openssl_sign($input,
  $sig, $key, 'sha256')` for ES256. So sign-side is provably feasible here.
- Cons: **verification is where JWT libraries earn their keep** — strict header validation, alg allowlisting,
  `none` rejection, RS256-vs-HS256 confusion defence, base64url canonicalisation, claim validation (`exp`/`nbf`/
  `iat`/`aud`/`iss`) with constant-time signature compare. Re-implementing this correctly is exactly the kind of
  security-critical crypto code the brief warns against, and a single subtle bug = token forgery / full auth
  bypass. High risk for marginal benefit.
- **Fit:** rejected as the primary path. *However* — we reuse the in-house sign technique as the
  documented precedent, and the in-house signer remains the fallback if a future audit forbids vendored code.

**Decision: Option A.** Vendor `firebase/php-jwt` source under `web/_lib/jwt/` (pinned, e.g. v6.10.x). Wrap it
in a thin project-owned `SIGNula\Security\Jwt` facade (`web/private_html/security/Jwt.php`) so:
- the rest of the codebase never calls `Firebase\JWT\*` directly (single swap point if we ever change libs);
- the facade enforces SIGNula policy (alg pin, iss/aud defaults, leeway, denylist check) in one place;
- G-001 has one clean dependency surface (`Jwt::sign()`, `Jwt::verify()`, `KeyManager::getJwks()`).

> **Vendoring task (manual, dev machine — has Composer locally per MEMORY.md):** run
> `php composer require firebase/php-jwt:^6.10` locally, copy `vendor/firebase/php-jwt/src/*.php` into
> `web/_lib/jwt/src/`, drop a `web/_lib/jwt/VERSION` and `web/_lib/jwt/LICENSE`. Do **not** ship the whole
> `vendor/` tree. Loaded via `require_once LIB_DIR . DIRECTORY_SEPARATOR . 'jwt' . DIRECTORY_SEPARATOR . 'src'
> . DIRECTORY_SEPARATOR . 'JWT.php'` (+ `Key.php`, `JWK.php`, `BeforeValidException.php`,
> `ExpiredException.php`, `SignatureInvalidException.php`) inside the `Jwt` facade with `file_exists()` guards
> per house style.

## 4. Algorithm & keys

### Algorithm: **RS256** (asymmetric, RSA-2048 minimum, RSA-3072 recommended)
- **Why asymmetric:** verifiers (G-001 relying parties, third-party services, even other internal services)
  must validate tokens **without holding a signing secret**. RS256 lets us publish only the *public* key via
  JWKS; the private key never leaves SIGNula. An HS256 (shared-secret) design would force every verifier to
  hold the secret — unacceptable for a platform whose whole point is multi-service trust.
- HS256 is **permitted only** for a narrow internal case if ever needed (same-process verify), but the default
  and the only externally-verifiable path is RS256. The `Jwt` facade **pins** the expected algorithm on verify;
  it never reads the alg from the token header to decide the key (that is the alg-confusion bug — see §7).

### Keys & `kid`
- A signing key is an **RSA keypair** identified by a `kid` (key ID = a random 16-byte hex or a timestamp-based
  slug, e.g. `2026-07-rsa1`). The `kid` goes in the JWT header so verifiers pick the right public key from JWKS.
- **Private key storage (in precedence order):**
  1. **`tblSettings`, `isSensitive=1`, encrypted** via `SecurityUtils::encrypt()` (AES-256-CBC, the existing
     mechanism). Key: `jwt.signing_key.<kid>.private_pem` (encrypted PEM), with `jwt.signing_key.active_kid`
     pointing at the current signer. This is the primary store and matches the brief ("settings… including
     credentials… stored in the database… isSensitive… cryptographically encrypted").
  2. **`_private` key-file fallback** per brief: PEM files under `web/_private/keys/jwt/<kid>.key` /
     `<kid>.pub` (dir `0700`, files `0600`, outside web root, `_`-prefixed). Used when DB is unreachable or as
     an operator preference. `KeyManager` reads DB first, file second, mirroring how `ENCRYPTION_KEY` itself
     lives in `web/_private/auth.php` today (`define('ENCRYPTION_KEY', …)`).
- **Public keys** are *not* sensitive: store the public PEM/JWK in `tblSettings` `isSensitive=0`
  (`jwt.signing_key.<kid>.public_jwk`) so the JWKS endpoint is a cheap read.
- **Note on the existing `ENCRYPTION_KEY`:** it is *not* salted per-row today (`SecurityUtils::encrypt` uses a
  random IV per call, which is sufficient for confidentiality; the brief's "salt" intent is met by the per-call
  IV). The JWT signing key is a *separate* secret from `ENCRYPTION_KEY` — `ENCRYPTION_KEY` *encrypts* the JWT
  private key at rest; it does not sign tokens.

### Key rotation story
- Multiple keys coexist: **JWKS publishes all currently-valid public keys** (active + recently-retired),
  so tokens signed by a key still inside any unexpired token's lifetime keep verifying.
- Rotation procedure (admin action + documented runbook):
  1. `KeyManager::generateKey()` mints a new RSA keypair + `kid`, stores encrypted private + public JWK.
  2. Set `jwt.signing_key.active_kid` = new `kid`. New tokens now sign with it.
  3. Old key's public JWK **stays in JWKS** until `now > (rotation_time + max_access_token_ttl)` — then
     `KeyManager::retireKey()` removes it from JWKS (optionally keeps the private key encrypted for forensic
     verification, or zeroises it).
  4. **Emergency rotation** (suspected key compromise): rotate active_kid, immediately drop the compromised
     `kid` from JWKS, and bulk-revoke (denylist) — see §5 revocation. Logged to `tblAdminAuditLog`.
- A settings flag `jwt.auto_rotate_days` (default 90) + a `BillingScheduler`-style cron task can warn/auto-mint
  when the active key ages out (non-destructive; never auto-retires a key still covering live tokens).

## 5. Token model

### Access token (short-lived, stateless, RS256 JWT)
Claims (registered + SIGNula):
| claim | value | notes |
|---|---|---|
| `iss` | `https://signula.id` (from `jwt.issuer` setting) | issuer — verified on every decode |
| `sub` | `userID` (string) | the SIGNula ID |
| `aud` | `https://signula.id/api` default; G-001 sets RP `client_id` | audience — verified |
| `exp` | `iat + jwt.access_ttl` (default **900s / 15 min**) | short |
| `iat` | issue time | |
| `nbf` | issue time | not-before |
| `jti` | random 16-byte hex | unique token ID — used for revocation/denylist |
| `scope` | space-delimited scopes (e.g. `user:read user:write`) | maps to existing `tblAPIKeys.permissions` scope vocabulary so authz is consistent across key+JWT auth |
| `kid` (header) | active signing key id | verifier selects public key |
| `typ` (header) | `at+jwt` | distinguishes access tokens (RFC 9068 style) |

Access tokens are **stateless** — verified by signature + claims, no DB hit on the hot path *except* a fast jti
denylist check (indexed, see below). This keeps the API fast while still revocable.

### Refresh token (long-lived, stateful, **opaque** — NOT a JWT)
- A high-entropy opaque string (`SecurityUtils::generateToken(64)`), **stored hashed** (SHA-256) in
  `tblRefreshTokens` — never stored or logged in plaintext (mirrors the `tblAPIKeys.keyHash` and the
  reset-token SHA-256 fixes C5 in MEMORY.md).
- Lifetime `jwt.refresh_ttl` (default **30 days**, sliding via rotation).
- **Rotation + reuse detection (cross-vendor table-stakes — Auth0/WorkOS/Supabase all do it):**
  - Each refresh token belongs to a **token family** (`familyID`). On `POST /auth/refresh`, the presented
    refresh token is looked up by hash; if valid + not-rotated, it is **marked rotated** (`rotatedAt` set,
    `replacedByID` linked) and a **new** refresh token in the same family is issued alongside a new access
    token. This is single-use rotation.
  - **Reuse detection:** if a refresh token that is *already rotated* (or revoked) is presented again, that
    signals theft (the attacker and the legitimate client both hold the token). Response: **revoke the entire
    family** (`tblRefreshTokens.revoked=1` for all rows with that `familyID`), raise a `SecurityAlert`
    (`SecurityAlertManager`), log to `tblActivityLog`, and return `401`. This is the standard refresh-token
    reuse-detection / automatic-reuse-detection behaviour.

### Revocation / denylist
- **Refresh tokens** are stateful → revoke by row (logout, family-reuse, admin action).
- **Access tokens** are stateless → use a **jti denylist** table `tblRevokedTokens` (jti, expiresAt). The
  `Jwt::verify()` facade checks the jti against this denylist (indexed lookup) and rejects denylisted jtis.
  Rows self-expire (a cron purge deletes where `expiresAt < NOW()`), so the denylist only ever holds *unexpired*
  revoked access tokens — bounded size. Because access TTL is 15 min, the denylist stays tiny.
- **Logout** (`POST /auth/revoke` with the access token, or session logout): denylist the access-token jti +
  revoke the refresh family.
- **Admin / emergency:** revoke all of a user's tokens (revoke all their refresh families + optionally bulk-add
  jtis is impractical for access tokens, so rely on short TTL — a user-level `tokensValidAfter` timestamp claim
  check is the lever: store `tblUsers.tokensInvalidBefore` and reject any access token with `iat <
  tokensInvalidBefore`). Add this column in migration 025.

### Coexistence with API-key and session auth
- `BaseController::getCurrentUser()` precedence stays: **session → bearer(JWT) → API key**. The only change is
  `getUserByToken()` becomes real.
- A Bearer JWT yields a `userID` (sub). An API key yields a `partnerID`. They live in different columns and
  resolve to different `currentUser` shapes — controllers already branch on this. Add a `'auth_method'` marker
  (`'jwt'` / `'api_key'` / `'session'`) onto `$this->currentUser` so controllers can enforce method-specific
  rules (e.g. some partner endpoints want `api_key` only).
- Scopes: JWT `scope` claim uses the **same scope vocabulary** as `tblAPIKeys.permissions`
  (`users:read`, `users:write`, …) so a single `hasScope()` check works for both. (This dovetails with FG-011
  entitlements later.)

## 6. Endpoints

All under the existing front-controller (`web/public_html/api/.htaccess` → `api/v1/index.php`), registered on
the `Router` exactly like current routes. `.well-known/jwks.json` needs an `.htaccess` rewrite to a handler
(see Stage 5).

### `POST /api/v1/auth/token` — issue tokens
- **Grant: password / session.** Body: `{ "email", "password" }` (+ MFA continuation if required) OR a
  valid browser session (issue tokens for the logged-in user, the "SPA bootstraps a token" case).
- Verifies credentials via existing `Auth::login()` semantics (account-status, lockout, MFA gate). On MFA
  required, returns a `mfa_required` challenge (do **not** issue tokens until MFA satisfied — reuse existing
  `MFA` flow / `MFAController`).
- On success: issue access JWT + refresh token (new family). Response:
  ```json
  { "success": true, "data": {
      "access_token": "<jwt>", "token_type": "Bearer",
      "expires_in": 900, "refresh_token": "<opaque>", "scope": "user:read user:write" },
    "meta": { ... } }
  ```
- **Heavily rate-limited** (see §7). Logs to `tblActivityLog` (success/failure, IP, UA).
- *Note:* the existing route `POST /api/v1/auth/refresh` is currently mapped to `AuthController@refresh`
  (a session-refresh stub). **Repoint/extend** it to the JWT refresh handler below; verify the old handler is a
  stub before replacing (it is referenced in `index.php` line 87).

### `POST /api/v1/auth/refresh` — rotate
- Body: `{ "refresh_token" }`. Validates (hash lookup, not rotated, not revoked, not expired), applies rotation
  + reuse detection (§5). Returns a new access+refresh pair. Reuse → family revoke + `401` + alert.

### `POST /api/v1/auth/revoke` — logout / revoke
- Body: `{ "token", "token_type_hint": "access|refresh" }` (RFC 7009 shape). Access → denylist jti; refresh →
  revoke family. Always returns `200` (RFC 7009: revocation is idempotent and does not leak token validity).

### `GET /.well-known/jwks.json` — public keys
- Returns `{ "keys": [ { "kty":"RSA","use":"sig","alg":"RS256","kid":"…","n":"…","e":"AQAB" }, … ] }` for all
  currently-valid public keys (active + not-yet-retired). Pure read from `tblSettings` public JWKs. Cacheable
  (`Cache-Control: public, max-age=3600`). No auth. **This endpoint is the shared contract with G-001.**

### Wiring into `requireAuth()`
Implement `BaseController::getUserByToken(string $token)`:
1. `Jwt::verify($token, ['typ' => 'at+jwt'])` → throws on bad sig/exp/alg/iss/aud/denylisted-jti.
2. On success, load the user by `sub` (reuse the private `getUserById()` path), confirm `accountStatus='active'`
   and `iat >= tokensInvalidBefore`.
3. Set `$this->currentUser` (+ `auth_method='jwt'`, `scope`, `jti`). Return it.
4. On any failure: return `null` (so `requireAuth()` emits the existing `401`) — **never** leak *why*
   (expired vs forged vs revoked) in the response body; log the detail to `tblErrorLog`/`tblActivityLog` only.

## 7. Security considerations

1. **Algorithm confusion / `none`:** the `Jwt` facade **pins** RS256 on verify and passes the expected
   algorithm to `firebase/php-jwt`'s `Key` object — it never trusts the token's own `alg` header to choose the
   verification path. `none` and HS256-where-RS256-expected are rejected. *This is the single highest-priority
   defence.* (CVE class: RS256→HS256 confusion where the RSA *public* key is misused as an HMAC secret.)
2. **`kid` injection:** `kid` is used only to *select* a key from our own JWKS set; it is never used as a file
   path or SQL fragment. Unknown `kid` → reject. (Prevents kid-based path traversal / SQLi.)
3. **Clock skew:** allow a small leeway (`jwt.leeway_seconds`, default **60s**) on `exp`/`nbf`/`iat` via the
   library's `JWT::$leeway`. No more — large leeway widens the replay window.
4. **`aud` / `iss` validation:** every decode verifies `iss == jwt.issuer` and `aud` contains the expected
   audience. G-001 tightens `aud` to the RP `client_id`.
5. **Constant-time compares:** signature compare is inside the vetted library (constant-time). Refresh-token
   hash compare uses `hash_equals()`. The existing `SecurityUtils::verifyCSRFToken()` already models this.
6. **Leakage in logs (ties to #30/#33):** **never** log raw tokens, refresh tokens, signing keys, or the
   `Authorization` header. Log only `jti`, `userID`, `kid`, outcome. Audit the new code against #30 (debug mode
   logging plaintext creds) — the token endpoint must redact `password`/`refresh_token` from any debug dump.
   Refresh tokens stored hashed only.
7. **Rate-limiting the token endpoint:** `POST /auth/token` is a credential-verification endpoint → wire the
   existing `RateLimitMiddleware` / `SecurityUtils::checkRateLimit()` per-IP **and** per-account (mitigates
   credential stuffing / brute force; complements `Auth`'s lockout). `/refresh` rate-limited per-IP too.
   `SecurityMiddleware::handleFormSubmission` semantics already exist to lean on.
8. **Transport:** tokens only over HTTPS (ties to #79 — production `.htaccess` HTTPS-force must be enabled before
   go-live). Document this as an operational gate.
9. **Token storage guidance (for client integrators, documented, not enforced server-side):** access token in
   memory; refresh token in an httpOnly secure cookie or secure storage — never localStorage for the refresh
   token. Put this in the API docs.
10. **CORS + credentials:** `Response::setCorsHeaders()` currently defaults `Access-Control-Allow-Origin: *`
    **with** `Allow-Credentials: true` — that combination is invalid/risky for credentialed requests. When JWT
    auth ships, recommend tightening `api.cors.allowed_origins` to an allowlist (flag this to the user; it is a
    pre-existing condition, fix-or-flag in Stage 4).
11. **No `X-Frame-Options`/security headers on API responses (#29):** add `X-Content-Type-Options: nosniff`
    and `Cache-Control: no-store` to token responses so tokens are never cached by intermediaries.

## 11. Acceptance criteria

- [ ] A client can `POST /api/v1/auth/token` with valid credentials (MFA-gated where required) and receive an
      RS256 access token + opaque refresh token; an invalid credential or rate-limit returns the correct
      `401`/`429` and is logged.
- [ ] `Authorization: Bearer <jwt>` authenticates a `requireAuth()` route; an **expired**, **tampered**,
      **`none`-alg**, **HS256-signed**, **wrong-`aud`/`iss`**, or **denylisted-jti** token is rejected with
      `401` and *no* reason leaked in the body.
- [ ] `POST /auth/refresh` rotates (single-use); replaying a rotated/revoked refresh token revokes the whole
      family, raises a security alert, and returns `401`.
- [ ] `POST /auth/revoke` denylists an access jti and/or revokes a refresh family idempotently (`200`).
- [ ] `GET /.well-known/jwks.json` returns valid JWK(s) that verify a freshly-issued token in an independent
      verifier (e.g. jwt.io / a test using a different lib).
- [ ] Existing **API-key** and **session** auth paths still work unchanged (regression).
- [ ] Signing private key is stored encrypted (`isSensitive`) and/or in a `0600` `_private` key file; no key,
      token, or refresh token appears in `tblActivityLog`/`tblErrorLog`/`error_log` (debug mode included).
- [ ] Key rotation: minting a new key, switching `active_kid`, and retiring the old key after TTL all work; old
      tokens keep verifying until expiry; emergency drop-from-JWKS revokes immediately.
- [ ] All new code: `SIGNULA_INIT` guard, `DIRECTORY_SEPARATOR`, prepared statements, PHP 8.3+ clean (`php -l`).
