# G-001 — SIGNula as an Identity Provider (OIDC + OAuth2 authorization server; SAML 2.0 IdP later)

> **Gate item:** FG-001 · **Status:** spec (queued, gated — large-architectural, security-critical, external-touching)
> **Depends on:** **G-003 (JWT API auth)** — reuses its `Jwt` facade, `KeyManager`, RS256 signing keys,
> `/.well-known/jwks.json`, and `tblRevokedTokens`. **G-003 Stages 1–4 must ship before G-001 Stage A2.**
> **Multi-cycle epic.** Phased A → B → C. Phase A is the buildable core; Phase B is designed-here / built-later;
> Phase C is noted only.
> **Author altitude:** build contract. This is the platform's single biggest capability gap *and* its
> crown-jewel attack surface — every security item in §5 is mandatory, not optional.

## 1. What & why

**Today SIGNula only *consumes* identity.** It is an OAuth *client/relying-party*: 9 social providers
(`web/private_html/auth/providers/{Google,Microsoft,Apple,Facebook,LinkedIn,PayPal,Yahoo,Amazon,WordPress}OAuth.php`)
let a user link a third-party account to their SIGNula ID. The `web/public_html/oauth/authorize.php` endpoint
is for SIGNula **calling out** — its own docblock says *"Initiate OAuth 2.0 authorization flow for delegate
email sending"* with purposes `email` (Graph/Gmail delegation) and `signin` (linking) — it redirects the user
*to* Google/Microsoft, it does **not** issue tokens *to* anyone. The base class `OAuth.php` is an abstract
**client** (cites RFC 6749/6750, holds *our* `clientId`/`clientSecret` *for the upstream provider*).
Grep confirms there is **no `id_token` issuance, no SAML assertion builder, no SAML library** anywhere in `web/`.

The brief's core promise is the inverse: *"a 'universal' all-in-one single login… used across a variety of
services… integration via a JSON-based API to exchange authentication."* That means SIGNula must **issue**
identity — let first- and third-party apps offer **"Sign in with SIGNula."** This is THE defining CIAM
capability (6/10 comparable platforms — Auth0, Keycloak, FusionAuth, Stytch, Descope, Frontegg — per FEATURES.md
FG-001).

**G-001 makes SIGNula an Identity Provider:** a relying-party (RP) app redirects the user to SIGNula; if the
user is logged in (or logs in), SIGNula authenticates them, asks consent, and returns signed tokens the RP can
verify — exactly the role Google/Microsoft play for SIGNula today, but now SIGNula is the IdP.

### End-to-end flow an RP integrates (Phase A, OIDC authorization_code + PKCE)

```
1. RP registers once (partner admin) → gets client_id (+ client_secret for confidential clients),
   registers exact redirect_uri(s), requested scopes.
2. User clicks "Sign in with SIGNula" in the RP app.
3. RP redirects browser → https://signula.id/oauth/authorize
      ?response_type=code&client_id=…&redirect_uri=…&scope=openid profile email
      &state=…&code_challenge=…&code_challenge_method=S256&nonce=…
4. SIGNula: validate client_id + EXACT redirect_uri match + scopes. If user not logged in → existing
   SIGNula login (password/MFA/passwordless/passkey — all existing flows). Then a CONSENT screen
   (skippable if previously consented to the same scopes).
5. User approves → SIGNula issues a single-use authorization CODE, redirects browser back to the RP's
   registered redirect_uri with ?code=…&state=… (state echoed for the RP's CSRF check).
6. RP backend calls POST https://signula.id/oauth/token
      grant_type=authorization_code&code=…&redirect_uri=…&client_id=…
      &code_verifier=…  (+ client_secret if confidential)
7. SIGNula validates the code (single-use, short TTL, PKCE verifier↔challenge, redirect_uri match, client
   match) → returns { access_token (JWT, G-003), id_token (JWT, OIDC), refresh_token, expires_in }.
8. RP verifies id_token signature against https://signula.id/.well-known/jwks.json (G-003 keys),
   checks iss/aud/exp/nonce → user is authenticated in the RP. Optionally calls GET /oauth/userinfo
   with the access_token for fresh claims.
```

Everything in steps 2–8 reuses G-003's signing keys + JWKS. The `id_token` is just a JWT with OIDC claims;
the access token is a G-003 access token scoped to the RP (`aud = client_id`).

## 2. Scope & phasing

### Phase A — OAuth 2.0 + OpenID Connect provider  *(buildable core — the bulk of G-001)*
- `GET/POST /oauth/authorize` — authorization endpoint (`response_type=code`, **PKCE required**).
- `POST /oauth/token` — token endpoint: `authorization_code` + `refresh_token` grants (and
  `client_credentials` for pure M2M RPs — optional, behind a per-client flag).
- `GET /oauth/userinfo` — OIDC UserInfo (Bearer access token → claims).
- `GET /.well-known/openid-configuration` — OIDC discovery document (advertises endpoints, scopes, claims,
  `id_token_signing_alg_values_supported: ["RS256"]`, `jwks_uri` → **G-003's** `/.well-known/jwks.json`).
- **`id_token` issuance** (JWT, OIDC standard claims) — signed by G-003 `Jwt::sign()`.
- **Consent screen** + scope enforcement; remembered consents.
- **RP client registration** — `tblOAuthClients` (client_id, hashed client_secret, redirect-URI allowlist,
  scopes, type public/confidential). Reuses `tblPartners` as the owning entity (a partner *is* the natural RP
  owner; a client belongs to a partner, alongside their `tblAPIKeys`).
- Authorization codes (`tblOAuthAuthCodes`), consents (`tblOAuthConsents`), access grants
  (`tblOAuthAccessGrants` — the issued-token ledger / revocation surface for RP tokens).

### Phase B — SAML 2.0 IdP  *(designed here, built in a later milestone)*
- Issue SAML 2.0 **assertions** to SAML Service Providers (enterprise apps that speak SAML, not OIDC).
- IdP **metadata** endpoint, **SP registration** (`tblSAMLServiceProviders`), attribute mapping, XML signing
  (and optional assertion encryption).
- Marked **later-milestone**: needs a vendored SAML/XML-signing library (no Composer in prod — §6), and SAML's
  XML-DSig/canonicalisation is a heavy, sharp-edged surface. Design captured in §3.B and §4 so the data model
  and endpoints are forward-compatible, but **do not build in the first G-001 pass.**

### Phase C — SCIM provisioning  *(NOTE ONLY — out of scope here)*
- Inbound SCIM 2.0 (RP/IdP pushes users *into* SIGNula) is a distinct, large capability. **Logged as a
  follow-on feature gap (suggest `FG-018 — SCIM 2.0 provisioning endpoint`)**, not designed in this spec.
  Outbound SCIM is explicitly out of scope per FEATURES.md.

### Out of scope for G-001 entirely
- Replacing the existing social-login *consumer* stack (unchanged).
- The partner self-serve SSO/branding portal (FG-015) — depends on G-001 existing; follow-on.
- Custom JWT claim templates per RP (FG-016) — follow-on on top of A.

### A. OIDC/OAuth2 provider design
- **Two endpoint styles:** `/oauth/authorize` and the consent screen are **browser-facing HTML** (user is
  present, redirects, renders a Bootstrap consent page) → built as page endpoints under
  `web/public_html/oauth/` like the existing `authorize.php`/`callback.php`. `/oauth/token`, `/oauth/userinfo`,
  and the two `.well-known` docs are **machine JSON** → built on the `Router`/`Response` stack (or standalone
  handlers mirroring the JWKS handler). This split matches the codebase's existing hybrid (pages via
  `.htaccess` rewrite, JSON via the front-controller).
- **Clean URLs / no visible `.php`:** `/oauth/authorize`, `/oauth/token`, `/oauth/userinfo`, and the discovery
  docs are served via the existing `.htaccess` rewrite (place handlers as `web/public_html/oauth/authorize.php`
  → URL `/oauth/authorize`, etc.). Discovery + JWKS need `.well-known` rewrites.
- **`id_token`** = JWT signed by G-003 with OIDC claims: `iss`, `sub` (the SIGNula `userID` — *pairwise* per-RP
  subject identifiers are a §5 hardening option), `aud` = `client_id`, `exp`, `iat`, `auth_time`, `nonce`
  (echoed from the authorize request — replay defence), plus profile/email claims per granted scope. `typ`
  header `JWT`; `kid` from G-003 active key.
- **access_token** = G-003 access token with `aud = client_id` and the RP-granted `scope`. The RP uses it at
  `/oauth/userinfo` and (later) at first-party APIs that accept SIGNula tokens.
- **Scopes (Phase A):** `openid` (required for OIDC), `profile`, `email`, `offline_access` (→ refresh token).
  Custom/partner scopes registered per client; the scope vocabulary aligns with `tblAPIKeys.permissions` +
  FG-011 entitlements so one `hasScope()` works across key/JWT/OIDC auth.
- **Client types:**
  - *Confidential* (server-side RP): has a `client_secret` (stored **hashed**), authenticates at `/oauth/token`.
  - *Public* (SPA / native / mobile): **no usable secret** → **PKCE (S256) is mandatory**, and the redirect-URI
    allowlist + `state` carry the security.

### B. SAML 2.0 IdP design (Phase B — later)
- **Assertion issuance:** on an SP-initiated SAML AuthnRequest (HTTP-Redirect/POST binding), authenticate the
  user (reuse existing login/MFA), then build a signed SAML 2.0 `<Response>`/`<Assertion>` with the SP's
  configured `NameID` format + attribute statement, POST it to the SP's ACS URL.
- **IdP metadata** endpoint (`/saml/metadata`) advertising the IdP entityID, SSO endpoints, and the signing
  certificate (an X.509 cert wrapping a public key — can share the RSA key material story with G-003, or a
  dedicated SAML signing cert; recommend a **dedicated cert** for SAML to keep protocols isolated).
- **SP registration** (`tblSAMLServiceProviders`): entityID, ACS URL(s), NameID format, attribute map, SP
  signing cert (for verifying signed AuthnRequests / encrypting assertions), wantAssertionsSigned, etc.
- **Crypto:** XML-DSig signing + canonicalisation (and optional XML-Enc) — **requires a vendored, audited PHP
  XML-security library** (§6). This is why Phase B is later and gated separately.
- Data model (sketch in §4) is added now-compatibly so Phase A migrations don't conflict, but the SAML tables/
  endpoints/library are **not built** in the first pass.

## 5. Security — the crown-jewel surface (all mandatory in Phase A)

1. **Redirect-URI EXACT-match allowlisting.** The `redirect_uri` in `/authorize` AND `/token` must
   **byte-exactly** match one of `tblOAuthClients.redirectURIs`. No prefix/substring/wildcard matching, no
   open redirects. This is the #1 OAuth IdP vulnerability (covert-redirect / token-theft). Reuse the spirit of
   `config.php`'s `sanitizeRedirectUrl()` open-redirect guard but enforce *exact allowlist*, not just
   same-origin.
2. **PKCE required.** `code_challenge`/`code_challenge_method=S256` mandatory for public clients and
   recommended (default-on) for all (`oidc.require_pkce=1`). Reject `plain` in prod (`oidc.allow_plain_pkce=0`).
   `/token` verifies `SHA256(code_verifier)` == stored `code_challenge`.
3. **Authorization-code single-use + short TTL.** Code is high-entropy, **stored hashed** (SHA-256, like
   `tblAPIKeys`/refresh tokens), TTL ~60s (`oidc.authcode_ttl`). On exchange, set `consumedAt` atomically; a
   **second use of the same code = replay** → revoke the associated `tblOAuthAccessGrants` + raise a
   `SecurityAlert` (RFC 6749 §4.1.2 / §10.5).
4. **`state` (CSRF) + `nonce` (replay).** `state` is the RP's responsibility but SIGNula round-trips it
   verbatim; `nonce` from `/authorize` is bound into the `id_token` so the RP can detect token replay. SIGNula's
   *own* authorize page also uses a CSRF token on the consent POST (reuse `SecurityUtils::generateCSRFToken()`).
5. **Mix-up defence.** The token response includes `iss` (the issuer), and the discovery doc pins it, so an RP
   talking to multiple IdPs can detect an IdP mix-up. Bind the code to `clientID` + `redirectURI` so a code
   minted for client A cannot be redeemed by client B.
6. **Client-secret hashing.** `client_secret` stored as `hash('sha256', $secret)` (never plaintext), shown once
   at registration — exactly the `APIKeyManager::generateKey()` precedent. Confidential-client auth at `/token`
   compares with `hash_equals()`.
7. **Consent + scope enforcement.** No token is issued for a scope the user did not consent to (or that the
   client is not allowed). First-party clients (`isFirstParty=1`) may skip the screen (still record consent).
   Downgrade-only: granted scope ⊆ requested ⊆ `allowedScopes`.
8. **Token-signing key isolation.** Reuse G-003's RSA keys via `Jwt`/`KeyManager` (private key encrypted in
   `tblSettings`/`_private`, never in code, never logged). SAML (Phase B) uses a *separate* signing cert to keep
   protocols isolated.
9. **RP token revocation.** Issued access tokens carry a `jti` recorded in `tblOAuthAccessGrants` → revoke via
   G-003's `tblRevokedTokens`. `offline_access` refresh tokens are G-003 refresh tokens (rotation + reuse
   detection apply). A user revoking consent in the hub revokes the grant + denylists the jti + revokes the
   refresh family.
10. **No-Composer self-hosted crypto/SAML libs (§6).** OIDC needs no new lib (G-003's JWT covers signing). SAML
    (Phase B) needs a vendored XML-security lib — called out explicitly.
11. **Input handling / SQLi / XSS (house security rules).** Every `client_id`/`redirect_uri`/`scope`/`state`/
    `code`/`code_verifier` is validated/typed before use; all DB access via prepared statements
    (`Database` wrapper). The consent screen escapes `clientName`/`logoURL`/scope descriptions with
    `htmlspecialchars(…, ENT_QUOTES, 'UTF-8')`. `redirect_uri` is validated against the allowlist *before* any
    redirect (prevents open redirect / reflected XSS via the error path — note the existing `authorize.php`
    error page already escapes, keep that).
12. **Rate-limiting & abuse.** `/token` and `/authorize` rate-limited (reuse `RateLimitMiddleware` /
    `SecurityUtils::checkRateLimit`). Brute-forcing codes is futile (single-use + 60s + hashed) but rate-limit
    anyway. Log every authorize/consent/token/revoke to `tblActivityLog` (+ admin actions to `tblAdminAuditLog`).
13. **Pairwise subject ids (option).** `oidc.subject_type=pairwise` issues a per-RP opaque `sub` (so colluding
    RPs cannot correlate the same user) — recommended for privacy-sensitive deployments; `public` (raw userID)
    is simpler. Decision deferred to operator via setting.

## 6. Dependencies (self-hosted, no Composer in prod)

- **Phase A (OIDC/OAuth2): no new library.** Signing is G-003's vendored `firebase/php-jwt` (`web/_lib/jwt/`).
  PKCE = `hash('sha256', …)` + base64url (native). Everything else is native PHP + the existing `Database`,
  `SecurityUtils`, `Auth`, `Router`/`Response`. ✅ This is *why* Phase A is the buildable core.
- **Phase B (SAML): one vendored XML-security library — explicit no-Composer call-out.** SAML XML-DSig
  signing/canonicalisation must use an audited lib, not hand-rolled XML crypto. Candidate:
  **`robrichards/xmlseclibs`** (the de-facto PHP XML-security lib; MIT) — vendored as source under
  `web/_lib/xmlseclibs/` exactly like `crawlerdetect`/`tcpdf`/`jwt`. A higher-level SAML toolkit
  (`onelogin/php-saml`) could wrap it but pulls more deps — prefer vendoring `xmlseclibs` + a thin in-house
  assertion builder. **Pin the version, add `_lib/xmlseclibs/VERSION` + `LICENSE`, track its GHSA feed.**
  *(Do not vendor until Phase B is approved.)*

## 7. Endpoints & UI

### Endpoints (Phase A)
- `GET/POST /oauth/authorize` — page (`web/public_html/oauth/authorize-idp.php` — NEW; **do not** clobber the
  existing consumer `authorize.php`, which serves a different purpose). Validates client/redirect/scope/PKCE;
  drives login + consent; issues code + redirects.
- `POST /oauth/token` — JSON handler (`web/public_html/oauth/token.php` → `/oauth/token`). `authorization_code`
  + `refresh_token` (+ optional `client_credentials`) grants. Uses G-003 `TokenService` + `Jwt::sign()` for
  access + builds `id_token`.
- `GET /oauth/userinfo` — JSON; Bearer access token → claims per granted scope.
- `GET /.well-known/openid-configuration` — discovery JSON (handler + `.htaccess` rewrite).
- `GET /.well-known/jwks.json` — **G-003's existing endpoint** (discovery `jwks_uri` points at it).

### UI
- **Consent screen** (Bootstrap, responsive, WCAG-compliant, no-JS-fallback per brief): shows RP name/logo,
  the scopes requested in plain language, Allow/Deny, "remember my decision". CSRF-protected POST.
- **Partner client registration** under the existing partner admin surface
  (`web/public_html/partners/admin/oauth-clients.php` — NEW): CRUD for `tblOAuthClients` (name, type, redirect
  URIs, scopes, regenerate secret — secret shown once). Mirrors the existing partner API-key management UX.
- **User "Connected Apps" hub page** (`web/public_html/settings/connected-apps.php` — NEW; distinct from the

## 9. Acceptance criteria (Phase A)

- [ ] A partner can register an OIDC client (public or confidential), define an **exact** redirect-URI
      allowlist + scopes, and (confidential) receive a `client_secret` shown once / stored hashed.
- [ ] `GET /oauth/authorize` rejects: unknown `client_id`, a `redirect_uri` not byte-matching the allowlist,
      a scope outside `allowedScopes`, a public client without PKCE, and `plain` PKCE in prod.
- [ ] A logged-in user is shown a consent screen (skippable for first-party / remembered consent), and on
      approval is redirected to the registered `redirect_uri` with a single-use `code` + echoed `state`.
- [ ] `POST /oauth/token` (authorization_code + PKCE) returns `access_token` (JWT, `aud=client_id`),
      `id_token` (valid OIDC claims incl. `nonce`, `auth_time`), and (offline_access) a rotating `refresh_token`
      — all verifying against `/.well-known/jwks.json` (G-003 keys) in an independent OIDC client.
- [ ] **Replaying a `code` revokes the grant** + raises a security alert; a code minted for client A cannot be
      redeemed by client B or a different redirect_uri.
- [ ] `GET /oauth/userinfo` with the access token returns claims matching the granted scopes only.
- [ ] `GET /.well-known/openid-configuration` is a valid OIDC discovery doc whose `jwks_uri`, `issuer`, and
      endpoint URLs are correct and `id_token_signing_alg_values_supported=["RS256"]`.
- [ ] A user can view and **revoke** a third-party app in the hub; revocation denylists tokens (G-003) so the
      RP can no longer act for that user.
- [ ] No client secret, code, token, or signing key appears in any log; all inputs validated/prepared; consent
      screen output escaped; all new files `SIGNULA_INIT`-guarded, `DIRECTORY_SEPARATOR`, PHP 8.3+ clean.
- [ ] Existing social-login *consumer* flows (`oauth/authorize.php`/`callback.php`) and API-key/JWT/session auth
      are unaffected (regression).

## 10. Test plan

- **Unit (`_tests/Unit/`):** `OAuthClientManagerTest` (redirect-URI exact-match incl. trailing-slash/case/port
  edge cases; scope subset; secret hash+verify); `PkceTest` (S256 verify, plain rejected); `AuthCodeTest`
  (single-use consume, TTL expiry, client+redirect binding); `IdTokenTest` (claims, `nonce` echo, `aud`,
  signed+verifiable via G-003 JWKS — reuse G-003 fixtures).
- **Integration (DB-gated, `_tests/Integration/`):** full authorize→consent→code→token→userinfo against a test
  client; refresh-token grant; code-replay revokes grant; consent revocation denylists tokens.
- **Adversarial (Stage A5, dev-team-security):** redirect-URI allowlist bypass attempts; PKCE downgrade/strip;
  scope escalation beyond consent/allowlist; mix-up (iss check); open-redirect via error path; consent-CSRF;
  client-secret confusion (public client presenting a secret).
- **Interop:** verify `id_token`/discovery against a known-good external OIDC verifier (oidc-debugger / a
  different-language client) to prove standards conformance.

## 11. Dependency note
**G-001 is built on G-003.** It adds *no* new signing primitive in Phase A — it composes G-003's
`Jwt::sign()` (for `id_token` + RP access tokens), `KeyManager`/JWKS (for RP verification), and
`tblRevokedTokens`/`tblRefreshTokens` (for RP token revocation + offline_access). Ship **G-003 Stages 1–4
before G-001 Stage A2.** Phase B (SAML) is the only part needing a new vendored library (`xmlseclibs`) and is
separately gated/later.
