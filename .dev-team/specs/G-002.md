## 0. CRITICAL SAFETY CONSTRAINT — TEST MODE ONLY

This engine is designed and built **exclusively against payment-provider TEST / SANDBOX endpoints with test keys**.

- **Every** provider call in this design resolves its credentials from `tblSettings` keys that are
  explicitly the **test/sandbox** variants (e.g. `payment.paypal.mode = 'sandbox'`,
  `payment.stripe.secret_key = sk_test_…`, `payment.coinbase.mode = 'sandbox'`). The engine **must
  refuse to run** any charge/subscription/refund call when a provider is in `live` mode (see §9.1).
- **No real money moves.** All renewals, dunning retries, proration charges, and refunds in scope
  execute against sandbox subscriptions/customers only.
- **Going live is a separate, USER-GATED operational step — GitHub issue #70 ("Configure Live
  Payment Provider Credentials").** This spec does NOT wire, request, or activate live credentials.
  The single act that flips the engine to production is the *user* setting live keys + `mode='live'`
  in `tblSettings` via the admin UI, after this engine is verified in sandbox. That step is out of
  scope here and must be called out in the build PR body.
- **No destructive / irreversible operations.** Migrations are additive only (new columns/tables,
  ENUM extensions). No `DROP`, no data-rewriting backfills beyond nullable-column defaults. Refunds
  are sandbox-only and provider-reversible.
- Tests **never** hit live endpoints — providers are mocked (see §11). CI has no live keys.

The build agent must treat "the engine works end-to-end in sandbox" as the definition of done for
G-002; "the engine is live" belongs to the user and #70.

## 1. What & Why

### 1.1 The gap (per issue #67 / FG-003)
SIGNula already has a large, well-formed billing surface (see §2). The promise of the brief —
"multi-tier subscriptions… paid tiers and features… payment via PayPal (also Apple/Google Pay),
crypto, configurable discounts per platform" — needs a **working recurring billing engine**: the
piece that, without a human, renews subscriptions, retries failed payments (dunning), prorates plan
changes, converts trials, issues renewal invoices, suspends/resumes on (non)payment, and keeps the
subscription state machine consistent with what the payment provider actually did (via webhooks).

`BillingScheduler` is **scaffolded but not functional end-to-end**. Grep-verified defects that
prove the gap (these are the core of the build):

1. **Schema ↔ code drift in `tblBillingSchedule` (BLOCKER).** Migration `012_payment_expansion.sql`
   defines the table with PK `scheduleID`, columns `completedAt`/`errorMessage`, and a `taskType`
   ENUM of `charge_subscription, suspend_subscription, resume_subscription, send_reminder,
   expire_trial, generate_invoice, process_remittance, fee_change_notification` and a `status` ENUM
   of `pending, processing, completed, failed, skipped`.
   But `BillingScheduler.php` reads/writes **`taskID`** (not `scheduleID`), **`result`**,
   **`nextRetryAt`**, **`lastAttemptAt`**, **`cancelled`** status, and task types **`suspend_account`,
   `calculate_usage`, `charge_usage`, `archive_usage`** that are **not in the migration ENUM**.
   On a clean install the engine throws on its first INSERT/UPDATE. *This is the #1 thing G-002 fixes.*

2. **`chargeStoredMethod()` does not exist (BLOCKER).** `BillingScheduler::executeProviderCharge()`
   calls `PayPalProvider::chargeStoredMethod()` / `StripeProvider::chargeStoredMethod()` /
   `CoinbaseProvider::chargeStoredMethod()`. **None of those methods exist** in any provider class
   (grep `function chargeStoredMethod` → 0 hits). The autonomous `charge_subscription` path
   dead-ends. (See §3 — the correct primary model is provider-managed subscriptions, not
   us pulling a stored-method charge.)

3. **No proration / upgrade / downgrade (gap).** `PaymentManager::createSubscription()` literally
   tells the caller "User already has an active subscription. Use upgrade/downgrade instead." — but
   **no `upgradeSubscription` / `downgradeSubscription` / proration method exists anywhere**
   (grep `proration|prorate|upgradeSubscription|downgradeSubscription|changeTier` → 0 hits).

4. **No webhook→state-transition mapping for subscription lifecycle.** Inbound webhooks are
   verified, deduped and logged (good — see §2/§7), and `handleWebhookEvent()` handles one-off
   `PAYMENT.CAPTURE.*` / `checkout.session.completed`, but the **recurring** lifecycle events
   (`BILLING.SUBSCRIPTION.*`, Stripe `invoice.paid` / `invoice.payment_failed` /
   `customer.subscription.*`) are not mapped onto `tblSubscriptions.subscriptionStatus`.

### 1.2 Scope

**In scope (TEST MODE):**
- Make `tblBillingSchedule` schema and `BillingScheduler` agree (migration 025 + minimal scheduler fixes).
- A documented **lifecycle state machine** over `tblSubscriptions.subscriptionStatus` (§5), with
  every transition driven by either a scheduler tick or a provider webhook, and **idempotent**.
- **Renewal** — for provider-managed subscriptions (PayPal Subscriptions, Stripe Billing) renewals
  are driven by provider webhooks; the scheduler only schedules reminders, reconciles drift, and
  drives the dunning/grace timers. Renewal invoices are issued on successful renewal.
- **Plan change** — `upgradeSubscription` / `downgradeSubscription` with **server-authoritative
  proration** (bcmath), immediate-vs-end-of-period semantics, provider subscription revision.
- **Cancel / reactivate** — extend existing `cancelSubscription` (immediate vs end-of-period) and
  add `reactivateSubscription` (within grace, before expiry).
- **Trial** — trial→active / trial→past_due conversion (extend existing `processTrialExpiry`).
- **Dunning** — configurable retry ladder + grace period + customer emails + final-cancel.
- **Scheduler** on Dreamhost (external cron + lazy safety-net, both already present) — harden,
  add advisory locking to prevent double-runs.
- **Entitlement tie-in** — subscription state is the source of truth FG-011 `Entitlements` reads (§8).

**Out of scope (explicitly):**
- **Going live / live credentials (#70)** — user-gated operational step (§0).
- **Re-implementing** `PaymentManager`, `InvoiceManager`, `CreditManager`, `UsageTracker`,
  `UsageBillingService`, provider classes, or the inbound webhook handlers. **Reuse them.**
  Duplicating any of these is a NON-GOAL and a review-fail.
- **Partner remittance/payout** logic (`processRemittance` stays a stub here; owned elsewhere).
- The **FG-011 entitlement enforcement layer** itself (sibling G-004) — G-002 only guarantees the
  subscription state it reads is correct.
- Net-new providers, Apple/Google Pay native sheets beyond what Stripe/PayPal already route (§3.4).
- Tax/VAT calculation engine (existing `taxAmount` columns are passed through, not computed here).

## 3. Provider Strategy (all TEST MODE)

The core architectural correction: **prefer provider-managed recurring subscriptions over
self-driven stored-method charges.** SIGNula does not hold card data, so it cannot (and must not)
build a "pull a stored card on a timer" engine for card payments. Instead:

### 3.1 PayPal — PRIMARY (provider-managed)
- Use **PayPal Billing Plans + Subscriptions API** (`PayPalProvider::createSubscription()` already
  exists). PayPal owns the recurring clock and charges the customer automatically each cycle.
- SIGNula stores the returned subscription id in `tblSubscriptions.paymentProviderSubscriptionID`
  (column already exists) and **reacts to webhooks**:
  - `BILLING.SUBSCRIPTION.ACTIVATED` → `trial|pending → active`
  - `PAYMENT.SALE.COMPLETED` / `PAYMENT.CAPTURE.COMPLETED` (recurring) → record payment, issue
    renewal invoice, advance period, clear dunning
  - `BILLING.SUBSCRIPTION.PAYMENT.FAILED` → enter dunning (`active → past_due`)
  - `BILLING.SUBSCRIPTION.SUSPENDED` → `past_due → grace`/`paused`
  - `BILLING.SUBSCRIPTION.CANCELLED` / `EXPIRED` → `canceled`/`expired`
- The scheduler's role for PayPal subs is **reconciliation + reminders + grace/dunning timers**, not
  charging. (This removes the dependency on the non-existent `chargeStoredMethod()`.)

### 3.2 Stripe — SECONDARY (TEST mode, provider-managed)
- Use **Stripe Billing** via `createCheckoutSession()` in **subscription mode** (exists). Stripe owns
  the recurring clock; SIGNula reacts to `invoice.paid`, `invoice.payment_failed`,
  `customer.subscription.updated/deleted` (map in §7). Test keys only (`sk_test_…`).

### 3.3 Crypto (Coinbase) & one-off — MANUAL-RENEW
- Crypto cannot be auto-charged. Coinbase subscriptions are modelled as **renew-by-invoice**: at
  `nextBillingDate − reminderDays` the scheduler emails a "renew now" link; if unpaid by
  `nextBillingDate + grace`, the subscription expires. `billingCycle='one_time'` and `'lifetime'`
  never schedule a renewal charge. The configurable **crypto discount** (`tblProviderDiscounts`,
  `PaymentManager::getProviderDiscount('crypto', …)`) applies at invoice generation.

### 3.4 Apple Pay / Google Pay — payment SHEETS, not providers
- Confirmed current state: settings + routing through Stripe/Stripe Payment Element / PayPal; **no
  standalone provider class**. They are **wallet UIs over Stripe/PayPal**, so they inherit whichever
  underlying provider's recurring model applies. G-002 does not add native sheets; it ensures a
  subscription created via an Apple/Google Pay sheet (i.e. underlying Stripe/PayPal sub) flows
  through the same lifecycle. (Native-sheet completion is a separate UI item, not billing-engine.)

### 3.5 "Free" subscriptions
- `amount <= 0` / `paymentMethod='free'` never call a provider; the scheduler just advances the
  period and keeps status `active` (already implemented — keep).

## 4. Subscription Lifecycle State Machine

States live in `tblSubscriptions.subscriptionStatus`. The migration ENUM already covers
`active, cancelled, expired, paused, trial, pending, past_due`. G-002 adds **`grace`** (see §6) to
distinguish "dunning retries exhausted, in grace window before suspension" from "first payment
failure" (`past_due`). `cancelled` is the existing spelling (keep — do not rename, that would be a
destructive migration). Map the FG-003 word "canceled" → existing `cancelled`.

### 4.1 States
| State | Meaning | Entitlements (FG-011) |
|---|---|---|
| `pending` | Created, awaiting first successful payment / provider activation | none / free |
| `trial` | In free trial (`trialEndsAt` in future) | full tier features |
| `active` | Paid & current (`currentPeriodEnd >= today`) | full tier features |
| `past_due` | A renewal payment failed; dunning retries in progress | full tier (soft) until grace |
| `grace` | Retries exhausted; grace window before suspension (`billing.grace_period_days`) | full tier (final warning) |
| `paused` | User-paused (existing `pauseSubscription`) | none / free, resumable |
| `cancelled` | Cancelled (immediate or at period end); `endDate` set | features until `currentPeriodEnd` if end-of-period |
| `expired` | Period ended with no renewal / grace lapsed | none / free |

### 4.2 Transitions (trigger → from → to)
```
                     ┌──────────── createSubscription() ───────────┐
                     ▼                                              │
   [pending] ──provider activated webhook──▶ [active]               │
   [pending] ──trial set (trialEndsAt)────▶ [trial]                 │
   [trial]   ──expire_trial tick, paid plan, 1st charge ok──▶ [active]
   [trial]   ──expire_trial tick, 1st charge fail──▶ [past_due]
   [trial]   ──expire_trial tick, free plan──▶ [active]
   [active]  ──renewal webhook: payment ok──▶ [active] (period advanced, invoice issued)
   [active]  ──renewal webhook: payment FAILED──▶ [past_due]  (dunning starts)
   [past_due]──dunning retry webhook ok──▶ [active]   (resume; auto-restore tier)
   [past_due]──retry ladder exhausted (scheduler)──▶ [grace]
   [grace]   ──payment ok before grace end──▶ [active]  (reactivate)
   [grace]   ──grace window lapses (suspend_subscription tick)──▶ [expired]  (+ provider cancel)
   [active|trial|past_due|grace] ──cancelSubscription(immediate)──▶ [cancelled] (endDate=today, provider cancel)
   [active] ──cancelSubscription(end-of-period)──▶ [active] autoRenew=0 → at period end ──▶ [expired]
   [cancelled|grace] ──reactivateSubscription() before currentPeriodEnd──▶ [active]
   [active|trial] ──pauseSubscription()──▶ [paused] ──resumeSubscription()──▶ [active]
   [any non-terminal] ──upgrade/downgrade──▶ [active] (proration, same status, new tierID)
```
- **Driver split:** *Provider webhooks* drive `pending→active`, renewal success/fail
  (`active↔past_due`), and provider-side cancel/expire. *Scheduler ticks* drive trial expiry, the
  dunning **timer** (escalate `past_due→grace→expired` when retries/grace lapse), reminders, and
  reconciliation. *User actions* (API/UI) drive cancel/reactivate/pause/resume/upgrade/downgrade.
- **Terminal states:** `expired`, `cancelled` (immediate). All others are recoverable.

### 4.3 Idempotency (a payment must NEVER double-charge)
1. **Webhook dedup (exists):** every inbound handler checks `tblInboundWebhooks` for
   `(provider, eventID, status='processed')` before doing work; a repeat is logged `duplicate` and
   returns 200. **Keep and rely on this** — it is the primary anti-double-charge guard for the
   provider-managed model.
2. **Idempotency keys on outbound calls:** any SIGNula-initiated provider mutation (proration
   charge, refund, subscription revision) MUST send a provider idempotency key derived from a stable
   business key: `sha256(action + subscriptionID + periodStart + amount + tierID)`. Store it in a new
   `tblBillingAttempts` row (§6) *before* the call; on retry, the same key is reused so the provider
   collapses duplicates. PayPal: `PayPal-Request-Id` header. Stripe: `Idempotency-Key` header.
3. **Payment uniqueness:** before recording a renewal payment, check for an existing
   `tblPayments` row with the same `transactionID` (provider txn id) — never insert twice.
4. **Task de-dup:** `createTask()` for a `charge_subscription`/`generate_invoice` first cancels any
   pending task of the same (taskType, target) (existing `cancelPendingTasks`) so reschedule can't
   stack two charge tasks for one period.
5. **Scheduler row claim:** `processDueTasks` claims tasks with a conditional
   `UPDATE … SET status='processing' WHERE scheduleID=? AND status='pending'` and only proceeds if
   the affected-row count is 1 (so two concurrent cron hits can't both grab the same task) — §10.

## 5. Renewal, Trial & Plan-Change Detail

### 5.1 Renewal (provider-managed primary path)
1. On `createSubscription`, persist `paymentProviderSubscriptionID`, `currentPeriodStart/End`,
   `nextBillingDate`, and schedule **reminders only** (existing `scheduleSubscriptionRenewal` but
   WITHOUT the `charge_subscription` task for provider-managed subs — gate that on
   `paymentMethod IN ('free')` OR a future stored-method path).
2. Provider charges at cycle end → webhook → handler records payment (`PaymentManager::recordPayment`
   + `completePayment`), `InvoiceManager::createInvoice($userID,'subscription',…, ['subscriptionID'=>…])`,
   advances `currentPeriodStart/End` + `nextBillingDate`, clears dunning, dispatches
   `subscription.renewed` outbound webhook.
3. `completePayment()` already calls `BillingScheduler::handlePaymentSuccess()` for auto-resume — keep.

### 5.2 Trial conversion
Extend existing `processTrialExpiry()`: for a paid plan with a provider subscription, do **not** try a
local charge — set `pending` and rely on the provider's first-cycle webhook; for `free`, set `active`.

### 5.3 Plan change with proration (NEW — `PaymentManager::changeTier()`)
Server-authoritative, bcmath, currency-safe.
```
changeTier(subscriptionID, newTierID, mode = 'immediate'|'period_end', actorUserID):
  authz: actor owns the subscription OR is admin (§9.4)
  newAmount  = server price of newTier for current billingCycle   // NEVER trust client
  oldAmount  = current tblSubscriptions.amount
  daysLeft   = currentPeriodEnd - today
  daysTotal  = currentPeriodEnd - currentPeriodStart
  unusedCredit = bcmul(oldAmount, bcdiv(daysLeft, daysTotal))      // time-weighted, 2dp
  proratedNew  = bcmul(newAmount, bcdiv(daysLeft, daysTotal))
  delta        = bcsub(proratedNew, unusedCredit)
  if mode == 'immediate':
     if delta > 0  (upgrade): create proration invoice for `delta`, charge via provider
                              (idempotency key, §4.3), revise provider subscription to new plan.
     if delta < 0  (downgrade): credit `abs(delta)` to CreditManager ledger (NO cash refund here),
                              revise provider subscription to new plan at next cycle.
     set tierID=newTierID, amount=newAmount, status stays 'active', period unchanged.
  if mode == 'period_end':
     queue a `generate_invoice`+plan-swap task for currentPeriodEnd; no immediate charge.
  log activity; dispatch `subscription.plan_changed` outbound webhook.
```
All arithmetic via **bcmath** (`bcmul/bcdiv/bcsub`, scale 2) — never native float — to avoid
rounding drift on money. Round half-up to the minor unit at the boundary only.

### 5.4 Cancel / reactivate
- Extend `cancelSubscription($id,$userID,$reason,$immediate)`: when a provider subscription exists,
  also call the provider cancel (PayPal `POST /billing/subscriptions/{id}/cancel`, Stripe
  `subscription.cancel`) in TEST mode; on `immediate=false` set `autoRenew=0` and let the period
  lapse to `expired`.
- Add `reactivateSubscription($id,$userID)`: allowed from `cancelled` (end-of-period, before
  `currentPeriodEnd`) or `grace`; re-enable autoRenew / re-activate provider sub; status→`active`.

### 6.3 `tblBillingAttempts` — NEW (per-charge audit + idempotency)
The anti-double-charge ledger; one row per *attempt* of a billable action.
```sql
CREATE TABLE IF NOT EXISTS `tblBillingAttempts` (
  `attemptID`       BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `subscriptionID`  INT UNSIGNED NOT NULL,
  `attemptType`     ENUM('renewal','proration','first_charge','dunning_retry','reactivation') NOT NULL,
  `provider`        VARCHAR(50) NOT NULL,
  `idempotencyKey`  CHAR(64) NOT NULL COMMENT 'sha256 stable business key; sent to provider',
  `amount`          DECIMAL(10,2) NOT NULL,
  `currency`        VARCHAR(3) NOT NULL DEFAULT 'GBP',
  `status`          ENUM('initiated','succeeded','failed','duplicate') NOT NULL DEFAULT 'initiated',
  `paymentID`       INT UNSIGNED DEFAULT NULL COMMENT 'tblPayments row once recorded',
  `providerTxnID`   VARCHAR(255) DEFAULT NULL,
  `failureCode`     VARCHAR(100) DEFAULT NULL,
  `failureMessage`  VARCHAR(1000) DEFAULT NULL,
  `attemptNumber`   TINYINT UNSIGNED NOT NULL DEFAULT 1 COMMENT 'Dunning attempt # in this episode',
  `mode`            ENUM('sandbox','live') NOT NULL DEFAULT 'sandbox' COMMENT 'Provider mode at attempt time',
  `createdAt`       DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `updatedAt`       DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`attemptID`),
  UNIQUE KEY `uniq_idempotency` (`idempotencyKey`),   -- ⛔ a key can exist once → no double charge
  INDEX `idx_ba_sub` (`subscriptionID`, `attemptType`),
  INDEX `idx_ba_status` (`status`),
  CONSTRAINT `fk_ba_sub` FOREIGN KEY (`subscriptionID`)
    REFERENCES `tblSubscriptions` (`subscriptionID`) ON DELETE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci
  COMMENT='Per-attempt billing ledger for idempotency + dunning audit';
```

## 7. Webhook → State-Transition Mapping

The inbound plumbing (verify → dedup → log → `handleWebhookEvent` → mark) is DONE per provider.
G-002 fills the **event→transition table** inside each provider's `handleWebhookEvent()` (and a shared
`BillingScheduler::applyLifecycleEvent($subscriptionID, $event, $data)` helper to keep logic in one
place). Processing is idempotent because of §4.3.

| Provider event (TEST) | SIGNula action | Status transition |
|---|---|---|
| PayPal `BILLING.SUBSCRIPTION.ACTIVATED` | activate sub, set period | `pending/trial → active` |
| PayPal `PAYMENT.SALE.COMPLETED` (recurring) | recordPayment+completePayment, renewal invoice, advance period, clear dunning | `active/past_due → active` |
| PayPal `BILLING.SUBSCRIPTION.PAYMENT.FAILED` | start/continue dunning | `active → past_due` |
| PayPal `BILLING.SUBSCRIPTION.SUSPENDED` | enter grace | `past_due → grace` |
| PayPal `BILLING.SUBSCRIPTION.CANCELLED` | cancel | `* → cancelled` |
| PayPal `BILLING.SUBSCRIPTION.EXPIRED` | expire | `* → expired` |
| Stripe `invoice.paid` | recordPayment, renewal invoice, advance, clear dunning | `active/past_due → active` |
| Stripe `invoice.payment_failed` | dunning | `active → past_due` |
| Stripe `customer.subscription.updated` (status) | reconcile to Stripe status | mirror |
| Stripe `customer.subscription.deleted` | cancel | `* → cancelled` |
| Coinbase `charge:confirmed` (renew invoice) | recordPayment, advance | `pending/past_due → active` |
| Coinbase `charge:failed/expired` | leave for grace/expiry timer | (scheduler-driven) |

**Replay protection:** in addition to the existing dedup, the handler must (a) reject events whose
provider timestamp is older than a configurable window for *state-moving* events where the provider
exposes one, and (b) never act on an event whose `eventID` is already `processed`. The signature
verification (`verifyWebhookSignature`) is the authenticity guard and must remain mandatory — an
unverified webhook is logged `verified=0` and **must not** drive a state transition (today some
handlers log-then-process; the build must ensure *no state change* on `verified=0`).

## 9. Security

### 9.1 TEST-MODE enforcement (hard guard)
A central `BillingScheduler::assertTestMode($provider)` / provider-level check reads
`billing.test_mode_guard` and the provider's `mode` setting; if guard is on and mode is `live`, the
call **throws and the task fails closed** (no charge). This is the code-level expression of §0 — it
makes "we accidentally went live" impossible without the user deliberately turning the guard off
(which is the #70 step). Every attempt records `mode` in `tblBillingAttempts`.

### 9.2 Amount / tier tampering — server-authoritative pricing
- Prices come **only** from `tblSubscriptionTiers` via `PaymentManager::getTier()`. The client may
  send a `tierID` and `billingCycle`; it may **never** send an amount. Proration amounts are computed
  server-side (§5.3). Any API that accepts an amount for a subscription action is a fail.
- Discounts validated server-side via `validateDiscountCode()` + `getProviderDiscount()`; codes are
  re-validated at charge time, not trusted from the session.

### 9.3 No card data (PCI scope minimisation)
- `tblPaymentMethods` stores tokens only (`providerMethodID`) — confirmed. The engine must never log,
  store, or transmit PAN/CVV. Card capture happens on the provider's hosted page / Element / PayPal,
  not on SIGNula. Debug logging must redact provider secrets and tokens (note existing issue #30 —
  do not regress it).

### 9.4 AuthZ + IDOR on subscription/invoice IDs
- Every billing action (cancel, upgrade, downgrade, reactivate, view invoice) verifies the actor
  **owns** the subscription (`tblSubscriptions.userID = currentUserID`) or is an admin/partner-admin
  with scope. IDs are opaque integers; the handler must `WHERE subscriptionID=? AND userID=?` (and
  for invoices `WHERE invoiceID=? AND userID=?`) — never trust the ID alone. CSRF token on every
  state-changing POST (per house rules). API actions go through `requireAuth()` / API-key scopes.

### 9.5 Webhook signature + replay (see §7)
Mandatory signature verify per provider; `verified=0` never drives state; dedup via
`tblInboundWebhooks(provider,eventID)`; cron endpoint stays `hash_equals`-token-guarded.

### 9.6 Concurrency safety on money
Charges are guarded by (a) the unique `idempotencyKey` in `tblBillingAttempts`, (b) the task row
claim (§10), and (c) `tblPayments.transactionID` uniqueness — three independent guards so a race or
a double cron tick cannot bill twice.

## 10. The Scheduler on Dreamhost (operational = #85, user)

- **Tier 1 — MySQL events** (exist): hourly, mark `past_due`, expire trials, mark overdue invoices.
- **Tier 2 — external cron** hitting `web/public_html/cron/billing.php?token=…` every 5–15 min
  (`processDueTasks`). **Creating the cron job is operational (#85) — the user does it**; the endpoint
  and token guard already exist.
- **Tier 3 — lazy safety-net** (`processLazyBatch`) on authenticated page loads if cron stale > 1h.

**Per-tick work:** claim due tasks (status+scheduledFor / nextRetryAt) → route by `taskType` →
reconcile subscriptions (new `reconcile_subscription` task: re-pull provider status for subs whose
`graceEndsAt`/`nextBillingDate` passed without a webhook, to self-heal missed webhooks) → escalate
dunning (`past_due` whose retry ladder is exhausted → `grace`; `grace` whose `graceEndsAt` lapsed →
`expired` + provider cancel) → send reminders → persist `billing.last_cron_run`.

**Locking to avoid double-runs (NEW):** two overlapping cron hits (or cron + lazy) must not process
the same task. Implement an **advisory claim**:
```
UPDATE tblBillingSchedule
   SET status='processing', lockToken=?, lockedAt=NOW()
 WHERE scheduleID=? AND status='pending'
   AND (nextRetryAt IS NULL OR nextRetryAt <= NOW());
-- proceed only if affected_rows == 1
```
A row stuck in `processing` longer than `billing.scheduler.lock_ttl_seconds` is reclaimable
(`processing` + `lockedAt < NOW()-TTL` → back to `pending`) to recover from a timed-out shared-host
request. Wrap the whole tick batch fetch + claim so the claim is the serialization point. (Optionally
take a MySQL `GET_LOCK('signula_billing_cron', 0)` around `processDueTasks` so only one cron run
executes at a time on shared hosting.)
