# G-004 — Multi-Jurisdiction Data-Protection / Compliance Tooling

> **Feature group:** FG-002 (umbrella) · **Foundational slice:** FG-002a (build first, autonomy-eligible)
> **Status:** SPEC (build-ready) · **Author:** privacy/compliance engineer · **Date:** 2026-06-30
> **Migration baseline:** next migration after `024` → **`025`–`028`** (one per layer; Layer 1 = `025`).
> **House rules in force:** PHP 8.3+ · MySQLi + prepared statements via `Database` wrapper · `SIGNULA_INIT` guard on every source file · `DIRECTORY_SEPARATOR` in all require/include paths · all config in `tblSettings` (`isSensitive`→`SecurityUtils::encrypt`) · clean URLs (no visible `.php`) · private dirs `_`-prefixed outside web root · emoji-annotated docblocks · static-method class library under `web/private_html/`.

---

## 0. Purpose, scope and the one hard rule

The brief (`.claude/CLAUDE.md`) enumerates **18+ data-protection regimes** and asks SIGNula to "build in functionality to **manage any data to comply** with the above." This spec designs the **machinery and the data-driven configuration model** to do that without code sprawl — **not** the legal content.

**The hard rule that shapes the whole design:** every jurisdiction-specific *number, right, threshold, window, and disclosure* lives in a **DB-configured regime model** (`tblComplianceRegimes` + child tables + `tblSettings`), never hardcoded in PHP. Adding the 19th regime is a row insert + a legal-text edit by the user, **zero code change**. PHP only knows the *shape* of a regime (it has rights, an SLA, an age threshold, a breach window), never the *values* for a named country.

## 1. Layered build plan (foundational slice first)

| Layer | Scope | Migration | Autonomy | Build order |
|------|-------|-----------|----------|-------------|
| **L1 — FG-002a** | Consent records + DSAR request tracker (wired to AccountManager) + admin queue + user request form | `025` | ✅ **YES** (autonomy-eligible — additive, reversible, no external/payment touch) | **FIRST** |

## 2. Layer 1 — Consent records + DSAR tracker (FG-002a) — **BUILD FIRST**

### 2.1 Data model — migration `025_consent_and_dsar.sql`

```sql
-- ============================================================================
-- 🛡️ Migration 025: Consent Records + Data-Subject-Request Tracker (FG-002a)
-- ============================================================================
-- Copyright (c) 2025-2026 MWBM Partners Ltd (t/a MWservices). All rights reserved.
-- Version: 2.7.0-beta · Description: foundational compliance plumbing.
--   - tblConsentRecords      : append-only consent audit trail (users + visitors)
--   - tblDataSubjectRequests : DSAR request tracker (delegates erasure/export to AccountManager)
--   - tblDataSubjectRequestEvents : per-request status/audit timeline
-- Extends, does NOT duplicate: tblDataExportRequests (mig 021), AccountManager, tblActivityLog.
-- ============================================================================

-- 🧾 APPEND-ONLY consent audit trail. One row per consent decision (grant OR withdraw).
-- Never UPDATE a row to flip a decision — INSERT a new superseding row (immutable history).
CREATE TABLE IF NOT EXISTS `tblConsentRecords` (
    `consentID`     BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    `userID`        BIGINT UNSIGNED NULL DEFAULT NULL
        COMMENT 'tblUsers.userID — NULL for pre-auth/anonymous visitors',
    `visitorID`     CHAR(36) NULL DEFAULT NULL
        COMMENT 'Anonymous UUID v4 (cookie-backed) for pre-login consent; reconciled to userID on signup',
    `consentType`   VARCHAR(64) NOT NULL
        COMMENT 'Free-but-conventional key: cookies.necessary, cookies.analytics, cookies.marketing, '
                'cookies.functional, marketing.email, terms, privacy_policy, data_processing, '
                'do_not_sell, parental — value set is data-driven, see tblConsentCategories (L2)',
    `granted`       TINYINT(1) NOT NULL
        COMMENT '1=granted/opt-in, 0=withdrawn/opt-out',
    `policyVersion` VARCHAR(32) NULL DEFAULT NULL
        COMMENT 'Version string of the policy/banner the decision was made against (see tblPolicyVersions, L2)',
    `mechanism`     ENUM('banner','preference_center','signup','api','gpc_signal','admin','import')
                    NOT NULL DEFAULT 'banner'
        COMMENT 'How the decision was captured — GPC auto-opt-outs are mechanism=gpc_signal',
    `regimeCode`    VARCHAR(16) NULL DEFAULT NULL
        COMMENT 'Resolved jurisdiction at capture time (FK-soft to tblComplianceRegimes.regimeCode, L3) — '
                'denormalised on purpose so the audit row is self-contained even if regime config changes',
    `ipAddress`     VARBINARY(16) NULL
        COMMENT 'IPv4/IPv6 stored as packed bytes via inet6_pton() — minimised; never plaintext geo',
    `userAgent`     VARCHAR(512) NULL,
    `proofHash`     CHAR(64) NULL
        COMMENT 'SHA-256 over (consentType|granted|policyVersion|ts|ip|ua) — tamper-evidence for audits',
    `createdAt`     DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (`consentID`),
    INDEX `idx_consent_user`    (`userID`, `consentType`, `createdAt`),
    INDEX `idx_consent_visitor` (`visitorID`, `consentType`, `createdAt`),
    INDEX `idx_consent_type`    (`consentType`, `granted`)
    -- NB: NO FK to tblUsers ON DELETE CASCADE — consent history must SURVIVE erasure as
    -- an anonymised compliance record (set userID=NULL on erasure, keep the row). See §2.4.
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci
  COMMENT='Append-only consent audit trail (FG-002a)';

-- 📨 DSAR tracker. Superset of tblDataExportRequests; for erasure/portability it DELEGATES.
CREATE TABLE IF NOT EXISTS `tblDataSubjectRequests` (
    `requestID`     BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    `userID`        BIGINT UNSIGNED NULL DEFAULT NULL
        COMMENT 'NULL allowed: a request can arrive by email before identity is matched',
    `requestType`   ENUM('access','portability','erasure','rectification','restriction',
                         'object','do_not_sell','withdraw_consent','automated_decision_optout')
                    NOT NULL
        COMMENT 'Union of rights across regimes; which apply per user is resolved from L3 config',
    `status`        ENUM('submitted','identity_pending','verified','in_progress',
                         'awaiting_user','fulfilled','rejected','partially_fulfilled','expired','withdrawn')
                    NOT NULL DEFAULT 'submitted',
    `regimeCode`    VARCHAR(16) NULL
        COMMENT 'Governing regime → drives dueDate SLA (resolved from tblComplianceRegimes, L3)',
    `requesterEmail` VARCHAR(255) NULL
        COMMENT 'For unauthenticated/email-channel requests; verified before fulfilment',
    `subjectRef`    VARCHAR(255) NULL
        COMMENT 'On-behalf-of reference (e.g. parent for a child, agent for data subject)',
    `details`       TEXT NULL COMMENT 'Free-text request detail (sanitised on input)',
    `rectifyPayload` JSON NULL COMMENT 'For rectification: proposed field→value changes (admin-reviewed)',
    `linkedExportID` BIGINT UNSIGNED NULL
        COMMENT 'FK to tblDataExportRequests.exportID when fulfilled via AccountManager::exportUserData()',
    `verificationToken` CHAR(64) NULL COMMENT 'SHA-256 of identity-verification token (never store raw)',
    `verifiedAt`    DATETIME NULL,
    `dueDate`       DATE NULL COMMENT 'Computed = submittedAt + regime SLA days (L3); admin-visible countdown',
    `assignedAdminID` BIGINT UNSIGNED NULL,
    `resolutionNote` TEXT NULL,
    `ipAddress`     VARBINARY(16) NULL,
    `submittedAt`   DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    `fulfilledAt`   DATETIME NULL,
    PRIMARY KEY (`requestID`),
    INDEX `idx_dsar_status_due` (`status`, `dueDate`),
    INDEX `idx_dsar_user`       (`userID`, `requestType`),
    INDEX `idx_dsar_export`     (`linkedExportID`)
    -- Soft link to tblDataExportRequests (no hard FK so erasure of the export row can't orphan a DSAR).
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci
  COMMENT='Data-subject-request tracker (FG-002a) — wraps AccountManager for erasure/portability';

-- 🕒 Per-request audit timeline (who did what when) — feeds the admin queue + compliance reports.
CREATE TABLE IF NOT EXISTS `tblDataSubjectRequestEvents` (
    `eventID`     BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    `requestID`   BIGINT UNSIGNED NOT NULL,
    `fromStatus`  VARCHAR(32) NULL,
    `toStatus`    VARCHAR(32) NOT NULL,
    `actorType`   ENUM('user','admin','system','cron') NOT NULL DEFAULT 'system',
    `actorID`     BIGINT UNSIGNED NULL,
    `note`        TEXT NULL,
    `createdAt`   DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (`eventID`),
    CONSTRAINT `fk_dsar_event_request` FOREIGN KEY (`requestID`)
        REFERENCES `tblDataSubjectRequests` (`requestID`) ON DELETE CASCADE,
    INDEX `idx_dsar_event_request` (`requestID`, `createdAt`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci
  COMMENT='DSAR status-change audit timeline';

-- ⚙️ Settings (data-driven SLA defaults; per-regime override comes in L3)
INSERT INTO `tblSettings` (`settingKey`, `settingValue`, `settingDescription`, `settingCategory`, `isSensitive`) VALUES

 ('dsar.identity_token.ttl_minutes','30','Lifetime of the DSAR identity-verification email token','privacy',0),
```

### 2.2 New class — `web/private_html/compliance/ConsentManager.php` (static)
`SIGNULA_INIT` guard; emoji docblocks; prepared statements via `Database`.
- `record(?int $userID, ?string $visitorID, string $consentType, bool $granted, array $opts): int` — INSERT append-only row; resolves `regimeCode` (L3, falls back to default), packs IP via `inet6_pton`, computes `proofHash` if enabled; logs `ActivityLogger::log($userID,'consent_'.($granted?'grant':'withdraw'),'privacy','info',…)`.
- `getCurrent(?int $userID, ?string $visitorID, string $consentType): ?array` — latest row by `createdAt`.
- `getEffectiveConsents(?int $userID, ?string $visitorID): array` — map of consentType→bool (latest each).
- `reconcileVisitorToUser(string $visitorID, int $userID): int` — on signup/login, stamp prior anonymous rows with the new userID (keeps trail continuous).
- `hasGranted(?int $userID, ?string $visitorID, string $consentType): bool`.

### 2.3 New class — `web/private_html/compliance/DSARManager.php` (static)
- `submit(array $req): int` — validate `requestType` against enum, sanitise `details`, resolve `regimeCode`+`dueDate` (L3; default `dsar.default_sla_days`), INSERT, write `tblDataSubjectRequestEvents` (submitted), notify admins (if `dsar.admin.notify_on_new`), `ActivityLogger::log`.
- `startIdentityVerification(int $requestID): void` / `verifyIdentity(int $requestID, string $token): bool` — SHA-256 token (mirror the `tblDataExportRequests.downloadToken` pattern), TTL from settings.
- `transition(int $requestID, string $toStatus, string $actorType, ?int $actorID, ?string $note): bool` — guarded state machine (see §2.5), appends an event row.
- **Fulfilment delegators (the anti-duplication seam):**
  - `fulfilPortability(int $requestID, int $userID, string $password): array` → calls `AccountManager::exportUserData($userID,$password)`, stores returned `exportID` in `linkedExportID`, transitions to `fulfilled`.
  - `fulfilAccess(int $requestID, int $userID): array` → same export engine (access = machine-readable copy); access vs portability differ only in framing/metadata.
  - `fulfilErasure(int $requestID, int $userID, string $password): array` → calls `AccountManager::requestAccountDeletion($userID,$password,$reason)`; transitions to `in_progress`; the existing grace-period + `processScheduledDeletions()` cron does the actual erasure; a follow-up event row + status flip to `fulfilled` happens when erasure completes.
  - `fulfilRectification(int $requestID, array $approvedChanges): array` → admin-approved field updates against `tblUsers`/`tblUserPreferences` (allowlisted columns only).
  - `applyDoNotSell(int $requestID, int $userID): void` → records a `do_not_sell` consent-withdraw via `ConsentManager::record(...granted:false)` (L2 toggle is the live switch).
- `getQueue(array $filters, int $limit, int $offset): array` — bounded pagination (cap `$limit`, guard `$offset` — heed B-014 lesson).
- `getComplianceReport(string $from, string $to): array` — counts by type/status, SLA-met %, overdue list.

### 2.4 Erasure-safety contract (CRITICAL — prevents a compliance own-goal)
`AccountManager::permanentlyDeleteAccount()` already anonymises `tblActivityLog` (sets `userID=NULL`, IP/UA `REDACTED`). The new tables MUST do the same, **not** cascade-delete:
- Add to `permanentlyDeleteAccount()` (the ONLY production-code edit this layer implies — a small, additive block, flagged for the build agent):
  `UPDATE tblConsentRecords SET userID=NULL, ipAddress=NULL, userAgent='REDACTED' WHERE userID=?` and
  `UPDATE tblDataSubjectRequests SET userID=NULL, requesterEmail=NULL, ipAddress=NULL WHERE userID=?`.
- Rationale: a regulator may ask "prove this user consented / prove you honoured their erasure" *after* the account is gone. The **fact of consent and the fact of fulfilment must survive**, the **PII must not**. This is why neither new table uses `ON DELETE CASCADE` to `tblUsers`.

### 2.5 DSAR state machine
`submitted → identity_pending → verified → in_progress → {fulfilled | partially_fulfilled | rejected}`; side-branches `awaiting_user`, `withdrawn`, `expired`. `transition()` enforces legal transitions in a `match`/allowlist; illegal transitions throw and are logged. Every transition writes a `tblDataSubjectRequestEvents` row.

### 2.6 Endpoints / UI (Layer 1)
- **User-facing request form** — extend `web/public_html/settings/privacy.php` with a new `request_dsar` POST action (CSRF-checked, like the existing `export_data`/`request_deletion`). Re-uses the page's auth/CSRF chrome. For pre-auth / "I can't log in" requests: a public form at `web/public_html/SIGNula.com/legal/data-request/index.php` (clean URL `/legal/data-request`) protected by CAPTCHA (`CaptchaVerifier`) + FormProtection; emails an identity-verification link.
- **Admin queue** — `web/public_html/admin/compliance/dsar/index.php` (clean URL `/admin/compliance/dsar`): list/filter/sort by status+dueDate, overdue highlighting, detail view with the event timeline, and fulfil buttons that call the `DSARManager` delegators. Gate via `AccessControl::requireSuperAdmin()` (or a new `compliance` capability check — see §6). AJAX actions in `web/public_html/admin/compliance/api/dsar-actions.php` (consistent error keys per B-011: `{success, data|error}`).
- **My consent history** — read-only section on `settings/privacy.php` listing the user's `tblConsentRecords` (what they agreed to + when + version).

### 2.7 Layer 1 acceptance criteria
1. Migration `025` applies cleanly via the existing migration runner; rollback documented.
2. Granting/withdrawing a cookie or marketing choice writes an append-only `tblConsentRecords` row with IP(packed)/UA/version/mechanism; **no row is ever UPDATEd** to flip a decision.
3. A user can submit each DSAR type from `settings/privacy.php`; an admin sees it in the queue with a correct `dueDate`.
4. **Portability/access** fulfilment produces a download via the *existing* `AccountManager::exportUserData` (linkedExportID populated); **erasure** routes through the *existing* `requestAccountDeletion`/`processScheduledDeletions` — **no second export/delete engine exists** (grep proves single implementation).
5. Permanent erasure anonymises (not deletes) consent + DSAR rows; the audit fact survives, PII does not.
6. Every state change is in `tblDataSubjectRequestEvents` and `tblActivityLog`.
7. Admin queue pagination is bounded (no unbounded LIMIT/OFFSET).

## 3. Layer 2 — Consent-management surface (migration `026`)

### 3.1 Server-side consent banner + preference center
Replace the localStorage-only banner in `public-footer.php` with a **server-persisted, granular, versioned** flow:
- **Granular categories** (data-driven, not hardcoded) — new `tblConsentCategories` (categoryKey, label, description, isStrictlyNecessary, defaultGranted, displayOrder, isActive). Seed: `necessary`(always on), `functional`, `analytics`, `marketing`. Banner renders categories from this table; "necessary" cannot be toggled off.
- **Anonymous visitor identity:** issue a `visitorID` UUID v4 in a first-party cookie (`SIGNULA_VID`, httponly off so JS can read for the banner, SameSite=Lax) so pre-login consent is recordable; `ConsentManager::reconcileVisitorToUser()` stitches it on signup.
- **Persistence:** banner choices POST to `web/public_html/api/v1/consent/index.php` (or a non-API `/legal/consent` endpoint for no-JS fallback) → `ConsentManager::record()` per category. JS still mirrors to localStorage for instant UX but the **server row is the source of truth**.
- **No-JS fallback:** a `<noscript>` link to a full-page consent form (brief requires everything work without JS/AJAX).

### 3.2 Versioned policy acceptance + re-consent
- New `tblPolicyVersions` (policyKey ENUM-ish: `terms|privacy|cookies`, version, effectiveDate, contentHash, isCurrent, changelog). Legal pages (`legal/*.php`) read the current version anchor from here.
- On login, `ConsentManager` checks whether the user's latest `terms`/`privacy` consent `policyVersion` matches `isCurrent`; if not → **re-consent interstitial** before proceeding. Records a fresh consent row on acceptance.

### 3.3 "Do Not Sell / Share" (CCPA/CPRA) + GPC
- A **"Do Not Sell or Share My Personal Information"** toggle on `settings/privacy.php` and a public `/legal/do-not-sell` link (CCPA requires a conspicuous link). Toggle = `ConsentManager::record(consentType:'do_not_sell', granted:false-means-opted-out)`.
- **Global Privacy Control (GPC):** detect the `Sec-GPC: 1` request header (and the `navigator.globalPrivacyControl` JS signal) in the bootstrap/middleware; when present and the resolved regime treats GPC as a valid opt-out (L3 flag), auto-record a `do_not_sell` opt-out with `mechanism='gpc_signal'` and reflect it in the UI. **Honoring GPC is required under CPRA/Colorado/Connecticut** — but *which regimes honor it* is an L3 config flag, not hardcoded.

### 3.4 Layer 2 settings
`consent.banner.enabled`, `consent.banner.style` (bar|modal|corner), `consent.reconsent.enforce`, `consent.gpc.honor` (master), `consent.visitor_cookie.name`/`.ttl_days`, `consent.do_not_sell.enabled`.

### 3.5 Layer 2 acceptance
- Granular consent persists server-side and survives cache clear / different device (keyed off userID once logged in).
- Changing the current policy version forces re-consent on next login.
- A `Sec-GPC: 1` request auto-records a do-not-sell opt-out where the regime config allows it, visible in consent history.
- Everything works with JS disabled (full-page fallback).

## 4. Layer 3 — Regime configuration model (migration `027`) — **the data-driven core**

This is what makes "18+ regimes without code sprawl" true. PHP never names a country; it reads rows.

### 4.1 Data model
```sql
-- 🌍 One row per regime. ALL jurisdiction values live here, never in PHP.
CREATE TABLE `tblComplianceRegimes` (
  `regimeID`        SMALLINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `regimeCode`      VARCHAR(16) NOT NULL UNIQUE COMMENT 'e.g. GDPR, UK_GDPR, CCPA, CPRA, VCDPA, HIPAA, COPPA, LGPD, PIPEDA, APPI, PIPA, POPIA, DPDP, PIPL, AU_PA88, NZ_PA20',
  `displayName`     VARCHAR(128) NOT NULL,
  `jurisdiction`    VARCHAR(64)  NULL COMMENT 'Country/region label — user-supplied',
  `dsarSlaDays`     SMALLINT UNSIGNED NULL COMMENT 'e.g. GDPR 30, CCPA 45, LGPD 15 — USER/LEGAL-SUPPLIED',
  `dsarExtensionDays` SMALLINT UNSIGNED NULL COMMENT 'permitted extension where regime allows',
  `breachNotifyHours` SMALLINT UNSIGNED NULL COMMENT 'authority window, e.g. GDPR 72h — USER-SUPPLIED',
  `breachNotifyAuthority` VARCHAR(255) NULL COMMENT 'supervisory authority name/contact — USER-SUPPLIED',
  `minAge`          TINYINT UNSIGNED NULL COMMENT 'digital-consent age, e.g. COPPA 13, GDPR-K 16 (configurable) — USER-SUPPLIED',
  `honorsGPC`       TINYINT(1) NOT NULL DEFAULT 0 COMMENT 'does this regime treat GPC as a valid opt-out',
  `requiresDoNotSell` TINYINT(1) NOT NULL DEFAULT 0,
  `lawfulBasisRequired` TINYINT(1) NOT NULL DEFAULT 0 COMMENT 'regime requires a recorded lawful basis (GDPR-style)',
  `isActive`        TINYINT(1) NOT NULL DEFAULT 0 COMMENT 'OFF by default — user activates after legal review',
  `isDraft`         TINYINT(1) NOT NULL DEFAULT 1 COMMENT 'seed rows ship as DRAFT — values are placeholders pending legal confirmation',
  `notes`           TEXT NULL,
  PRIMARY KEY (`regimeID`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

-- 🔗 Many-to-many: which rights a regime grants (maps to tblDataSubjectRequests.requestType)
CREATE TABLE `tblRegimeRights` (
  `regimeID` SMALLINT UNSIGNED NOT NULL,
  `right`    VARCHAR(40) NOT NULL COMMENT 'access|portability|erasure|rectification|restriction|object|do_not_sell|withdraw_consent|automated_decision_optout',
  PRIMARY KEY (`regimeID`,`right`),
  CONSTRAINT `fk_rr_regime` FOREIGN KEY (`regimeID`) REFERENCES `tblComplianceRegimes`(`regimeID`) ON DELETE CASCADE
) ENGINE=InnoDB;

-- 📜 Required disclosures per regime (drive privacy-page sections; CONTENT is user-supplied)
CREATE TABLE `tblRegimeDisclosures` (
  `disclosureID` INT UNSIGNED NOT NULL AUTO_INCREMENT,
  `regimeID` SMALLINT UNSIGNED NOT NULL,
  `disclosureKey` VARCHAR(64) NOT NULL,
  `title` VARCHAR(255) NULL,
  `body`  TEXT NULL COMMENT 'USER/LEGAL-SUPPLIED disclosure text — ships empty',
  PRIMARY KEY (`disclosureID`),
  CONSTRAINT `fk_rd_regime` FOREIGN KEY (`regimeID`) REFERENCES `tblComplianceRegimes`(`regimeID`) ON DELETE CASCADE
) ENGINE=InnoDB;

-- 🗺️ Resolution rule: map a request to a regime (by country code, partner override, or user-declared residency)
CREATE TABLE `tblRegimeResolution` (
  `ruleID` INT UNSIGNED NOT NULL AUTO_INCREMENT,
  `matchType` ENUM('country','region','partner','default') NOT NULL,
  `matchValue` VARCHAR(64) NULL COMMENT 'ISO country code, region, or partnerID',
  `regimeID` SMALLINT UNSIGNED NOT NULL,
  `priority` SMALLINT NOT NULL DEFAULT 100 COMMENT 'lower = evaluated first',
  PRIMARY KEY (`ruleID`),
  INDEX `idx_resolution` (`matchType`,`matchValue`,`priority`)
) ENGINE=InnoDB;
```
Seed the 18+ regimes from the brief as **`isActive=0, isDraft=1`** rows with **NULL/placeholder** SLA/age/breach values and a `notes='⚠️ Values pending legal confirmation'`. The migration ships the *skeleton* (one row per named regime so the user has a checklist); the *values* are a user task.

### 4.2 New class — `web/private_html/compliance/RegimeResolver.php` (static)
- `resolve(?int $userID, ?int $partnerID, ?string $countryHint): array` — walk `tblRegimeResolution` by priority → return the active regime row (or the most-protective default). Country hint from user-declared residency first, then a coarse IP-country lookup if available (no new geo dependency required — degrade to default).
- `slaDaysFor(string $regimeCode): int`, `minAgeFor(string $regimeCode): int`, `breachWindowHours(string $regimeCode): int`, `rightsFor(string $regimeCode): array`, `honorsGPC(string $regimeCode): bool`.
- **Most-protective fallback:** if no regime resolves or values are NULL, fall back to `dsar.default_sla_days` (30) / strictest age — never fail open.
- `DSARManager::submit()` and `ConsentManager::record()` call this to stamp `regimeCode`/`dueDate`. **This is the single integration point that keeps everything data-driven.**

### 4.3 Admin UI
`web/public_html/admin/compliance/regimes/index.php` — CRUD over regimes/rights/disclosures/resolution rules (super-admin only). A "draft → active" workflow: a regime cannot be activated until SLA + minAge + breach window are non-NULL (forces the user to fill the legal values). `logAdminAction()` on every change.

### 4.4 Layer 3 acceptance
- Adding a brand-new regime (the "19th") = inserting rows in 4 tables via the admin UI, with **zero PHP edits** (grep proves no regime code literal anywhere in `web/private_html`).
- A DSAR's `dueDate` is computed from the resolved regime's `dsarSlaDays`, falling back to the default.

## 6. Security & privacy of the compliance data itself

The compliance store is **higher-sensitivity than ordinary app data** (it is the evidence a regulator inspects). Controls:
- **Access control:** all admin compliance UI/endpoints gate via `AccessControl` — require `super-admin` (or introduce a `compliance` capability mapped into `ROLE_HIERARCHY`; keep it ≥ `admin=60`). No partner-level user sees another partner's DSARs/consent.
- **Audit-of-the-auditors:** every admin action on compliance data writes `AccessControl::logAdminAction()` + `tblActivityLog`. The compliance tables are append-mostly; status changes are event-sourced (`tblDataSubjectRequestEvents`).
- **PII minimisation:** IPs stored **packed** (`VARBINARY(16)` via `inet6_pton`), never with derived geo; UA truncated. Identity-verification + download tokens stored as **SHA-256 hashes**, never raw (mirror `tblDataExportRequests.downloadToken` lesson C5). `rectifyPayload`/`verificationToken` handled as sensitive.
- **No leakage:** DSAR/consent JSON is never echoed unescaped; all admin output through `htmlspecialchars(...,ENT_QUOTES,'UTF-8')`; AJAX returns `{success,data|error}` (B-011) and sets `X-Frame-Options: DENY` (heed #29). Public data-request form is CAPTCHA + FormProtection + rate-limited (no DSAR-spam / enumeration: never reveal whether an email matches an account — always respond "if an account exists, we've emailed verification").
- **CSRF:** every state-changing POST verifies `SecurityUtils::verifyCSRFToken()` (matches `settings/privacy.php` pattern); fix the #28 GET-action gap by making all compliance admin mutations POST-only.
- **Encryption:** any free-text that could hold special-category data (breach summaries, RoPA notes) is stored in TEXT; if the user marks a setting `isSensitive` it is `SecurityUtils::encrypt`ed by the existing settings loader. Secret cron token is `isSensitive`.
- **Erasure-safe (see §2.4):** PII anonymised on erasure, audit fact retained.

## 10. Top 5 risks
1. **Erasure ↔ audit conflict (highest).** A naive `ON DELETE CASCADE` would wipe the very consent/DSAR proof a regulator demands; the §2.4 anonymise-don't-delete contract (and the small additive edit to `permanentlyDeleteAccount()`) is mandatory and easy to get wrong. Mitigation: no hard FK to `tblUsers`, explicit anonymisation step, integration test.
2. **Legal-content leakage into code.** The whole value proposition is data-driven config; a build agent hardcoding "GDPR = 30 days" anywhere defeats it and creates wrong-by-jurisdiction behaviour. Mitigation: grep-gate in AC (no regime literals in PHP), draft-only seeds, resolver as single integration point.
3. **Auto-purge data loss.** A retention policy that runs while values are unconfirmed could irreversibly delete user data. Mitigation: `retention.purge.enabled=false` + `dry_run=true` by default, batch caps, admin activation workflow, `anonymise` preferred over `delete`.
4. **DSAR endpoint as an attack surface.** The public data-request form invites enumeration/spam and could be abused to trigger another user's erasure/export. Mitigation: identity verification before fulfilment, uniform "if an account exists…" responses, CAPTCHA + FormProtection + rate-limit, never act on an unverified request.
5. **Reinventing AccountManager (scope creep / duplication).** Pressure to "just write our own export for DSAR" would fork the GDPR engine and let the two drift. Mitigation: `DSARManager` is a thin wrapper that *only* delegates for erasure/portability/access; AC item asserts a single export/delete implementation by grep.
